# 上下文工程（Context Engineering）

## 核心洞察

> 不管是思维链、Tool Use、Agent 循环、MCP 工具描述还是 Skills 文档，**最终都要塞进上下文窗口里，交给同一个概率模型去一个字一个字地往外蹦**。

LLM 所有高级能力（推理、工具调用、Agent 循环）的本质，都是在上下文中塞入不同类型的信息：

| 概念 | 在上下文中的本质 |
|------|------------------|
| 思维链 | 模型在上下文里写给自己看的草稿 |
| MCP / Tool Use | 上下文里塞工具描述，模型输出调用请求，结果追加回上下文 |
| Agent 循环 | 不断往上下文里追加思考和工具结果 |
| Skills | 把操作手册文本加载到上下文里 |

## 关键公式

**上下文里塞什么、怎么塞、塞多少 → 直接决定 Agent 表现。**

这揭示了一个重要事实：所谓「Agent 工程」，本质上是**上下文工程**——如何高效地组织和填充 LLM 的上下文窗口。

## 上下文窗口的约束

- 上下文 = 输入问题 + 对话历史 + 系统背景设定（System Prompt）
- 主流窗口大小：128K ~ 1M token
- 超出窗口的内容被压缩或丢弃（「失忆」）
- **最佳实践**：一个上下文窗口只聚焦一个问题，新问题重新开窗口

## Agent 工程的差异

以 Claude Code 为例，它比 Cursor 等 API 调用方式效果更好的关键原因：

- Claude Code 敢给模型塞更多上下文，获取充分信息后再执行
- API 调用受成本限制，倾向于塞更少上下文尽快给答案
- **同样能力的模型，上下文填充策略不同 → 效果差距巨大**

## 换个方向看：不是「塞多少」，而是「谁有写权限」

上面这套「本质都是往窗口里塞信息」的框架，容易把上下文工程读成一道**填充量**问题——塞得够多够全就好。放到多步 Agent 的闭环里，这个直觉会翻面：真正决定成败的不是塞多少，而是**错误信息能不能拿到写权限**。[[2026-07-20-react-agent-error-compounding]]

单步问答里一次预测错了，损失停在那一步；[[react-agent]] 循环里 `Action` 会改写外部世界、选择下一条数据，`Observation` 被截断摘要后回灌进 `Context`，于是**一个早期小偏差会改变后续每一步看到的世界**，沿闭环自激放大。此时窗口里多塞的每一段未标来源的推断、每一次被压成「已确认」的猜测，都不是「信息更全」，而是给错误发了一张长期居留证。所以上下文工程的对象不是 token 数量，而是**什么信息以什么证据等级、什么生命周期进入下一轮决策**。

据此，它落地成分布在回路各接口的一组「写权限闸门」，而非一句更好的 system prompt：

| 接口 | 拦的是 | 手段 |
|------|--------|------|
| 动作前 | Thought→Action 的翻译误差 | 自由文本压成 typed schema + 参数/副作用/权限校验，写操作先 dry-run，参数带实体 ID 而非易混名字 |
| 观察入窗前 | Observation 的测量污染与来源漂白 | 区分 `empty/timeout/permission_denied/parse_error`，原始证据与摘要并存且摘要指回 source span，外部文本按不可信数据隔离、不给指令权 |
| 历史压缩时 | Context 里「猜测升格为事实」 | 用分栏账本拆开 Goal / Facts(带 source) / Hypotheses / Plan / Failures，别让一段自然语言摘要背所有状态 |
| 循环过程中 | 错误的自我复制 | loop detector、按错误类型分配重试预算、无信息观察后强制换查询/工具、checkpoint 重规划而非续喂脏轨迹 |
| 提交前 | 「内部自洽」被误当「外部正确」 | 可执行断言（数字能否定位 source span、实体 ID 是否全程一致）而非同分布的「请再检查一遍」|

一个由此推出的判据：**上下文压缩 vs 精确填充的 trade-off**（见下方开放问题）本质是「压缩会不会顺手把『未验证』压成『已确认』」——压缩不是无损缩短，而是一次改写记忆的机会，最危险的丢失不是丢 token，而是丢证据等级。闭环最终收敛还是发散，取决于三个变量：**observability**（错误在反馈里是否留下可辨信号）、**diagnosability**（能否区分无结果/工具故障/参数错/假设错）、**recoverability**（识别后有无回退换路）——三者弱时，往窗口里多塞一轮反思只是给错误更多自我解释的机会。

## 再换一根轴：把手段按「切断哪类故障、错误能传多远」重排（故障域设计）

上一节的闸门表按 ReAct 回路的**接口位置**排（动作前 / 观察入窗 / 历史压缩 / 循环中 / 提交前）。还有一根更本质的轴：不问「在回路哪一步拦」，而问「切断的是哪一类故障、这类故障默认能传播多远」——同一批手段读成**故障域（failure domain）设计**，就多出一层不靠 prompt 也不靠更强模型的可靠性结构。[[2026-07-27-context-engineering-error-firebreaks]]

四种手段各切一类不同故障，且每一种都不是消灭风险、而是把风险**搬运**到更可控的位置（引入一种新损失）：

| 手段 | 切断的故障 | 发生位置 | 新引入的风险 | 验证方式 |
|------|-----------|---------|------------|---------|
| Compaction | 噪声**纵向**累积（每轮工具回显只用一次却一起回灌） | 历史 → checkpoint | 摘要漂移、漏约束 | 恢复性检查 + 原文指针可回查 |
| 子代理隔离 | 错误**横向**扩散（一条脏上下文污染其余判断） | 主上下文 ↔ 局部上下文 | handoff 失真、局部最优 | 结构化可审计交付 + 独立验证 |
| 按需检索 | 无关材料**争抢注意力**（可能相关但当前无关的文本稀释信号） | 窗口外 → 工作集 | 漏召回、不知自己不知 | 需求触发 + 强制回源 |
| 外部记忆 | 跨窗**状态丢失**（超窗后关键约束消失） | 工作记忆 → 持久层 | 过期错误被永久化 | 来源 / 时间 / 作用域 / 覆盖失效规则 |

四招不能互相替代，因为它们控制的是信息生命周期的不同环节——这也解释了「多塞 token 救不了长任务」：容量从来不是这四类故障里的任何一类。其中 compaction 那道保险丝，正是 [[react-agent]] 页记的「分栏账本」——`Goal / Facts(带 source) / Hypotheses / Failures` 分槽，本质是**拒绝在 Agent 记忆环上过早聚合**（把「未验证」压成「已确认」＝编码端单向量、评测端单指标同一病灶的第四处发作，见 [[2026-07-25-aggregation-erases-minority-signals]]）。

### 杀伤力在于它和分布式系统的故障隔离是同一个形状

```text
compaction   <-> log compaction / checkpoint
子代理隔离   <-> bulkhead / failure domain
按需检索     <-> lazy loading / cache miss
外部记忆     <-> durable state / database
```

分布式系统不假设机器永不宕机，而是设计超时、重试、幂等、隔离舱、检查点与恢复。上下文工程同样不该假设模型永不误读——**可靠性不来自某个组件绝不犯错，而来自错误发生后不被无限放大、且系统能从中恢复**。这正是上一节 observability / diagnosability / recoverability 三变量的上位表达：三者是「错误留没留信号、能不能定位到层、定位后能不能回退」。

### 把 compaction 这道保险丝落到生产实现：它自己也是一段有状态、会过期的缓存

上面把 compaction 讲成一道抽象保险丝（切「噪声纵向累积」、代价是「摘要漂移、漏约束」）。一份生产级 coding agent（Grok Build）的两阶段 compaction 给这道保险丝补了一层平时被略过的真相——**保险丝本身也是一个组件，也会故障、也需要它自己的保险丝**。[[2026-07-26-grok-build-architecture]]

它的机制拆成两趟，恰好对上表里 compaction 那一行的两个空缺：

- **Pass 1（prefire，异步预烧）**：在 token 逼近阈值前留一段提前量（default_lead≈10%）就在后台先把历史前缀摘成 NOTE₁；真正触发 compaction 时只需把 NOTE₁ 拼上最近尾部再摘一次。这把「压缩」从一次**同步卡顿**改成大部分工作提前摊掉——对应「恢复路径不能自己变成新的停顿源」，并另配 `wall_clock_budget`（默认 300s）兜住 reasoning 模型摘要跑飞，正是 recoverability 落到 compaction 自身。
- **Pass 2（tail）+ 指纹失效**：`fingerprint_prefix()` 对前缀 item 的类型+文本做 hash，一旦历史被 rewind / branch / 编辑，指纹变了就丢弃 NOTE₁ 重摘。

第二点才是给全页添的新洞见：**预烧出来的 NOTE₁ 是一份缓存，而缓存最危险的失效模式不是「摘错」而是「摘的是一段后来被改写掉的历史」**——这正是上表 external-memory 行里「过期错误被永久化」那类故障，如今在 compaction 内部复发。于是同一副[[2026-07-25-aggregation-erases-minority-signals|拒绝把「未验证」聚合成「已确认」]]的骨架又多一层：不仅摘要时别把猜测压成事实，缓存的摘要在底层事实被 rewind 后还得能**自证过期**。指纹失效＝把「durable state 的失效规则」（上表 external-memory 那行的验证方式：来源/时间/作用域/覆盖失效）搬进 compaction——一道保险丝要可靠，得先假设它自己会指向一段不再成立的世界。

据此可以把本页开头的定义再抬一层：

> 上下文工程 = 为 Agent 设计信息的**边界、寿命与恢复路径**。窗口大小是**容量**指标；**错误传播半径与恢复能力**才是**可靠性**指标。

它给出一个比「最终答案正确率」更硬的验收法——**故意注入四类故障**再看错误会不会越界：① 历史里放一条已过期的错误假设；② 让一个子任务接触被污染 / 恶意材料；③ 把关键证据藏进默认未加载的长文档；④ 外部记忆里放一条已被新事实覆盖的旧记录。然后只问三件事：错误是否越过边界？系统能否定位它来自哪一层？有无不依赖人工重启整个任务的恢复路径？——这比「窗口支持 1M token」更能说明系统是否可用。
