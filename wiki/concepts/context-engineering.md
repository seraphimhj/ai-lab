# 上下文工程（Context Engineering）

## 核心洞察

> 不管是思维链、Tool Use、Agent 循环、MCP 工具描述还是 Skills 文档，**最终都要塞进上下文窗口里，交给同一个概率模型去一个字一个字地往外蹦**。

LLM 所有高级能力（推理、工具调用、Agent 循环）的本质，都是在上下文中塞入不同类型的信息：

| 概念 | 在上下文中的本质 |
|------|------------------|
| 思维链 | 模型在上下文里写给自己看的草稿 |
| MCP / Tool Use | 上下文里塞工具描述，模型输出调用请求，结果追加回上下文 |
| Agent 循环 | 不断往上下文里追加思考和工具结果 |
| Skills | 把操作手册文本加载到上下文里 |

## 关键公式

**上下文里塞什么、怎么塞、塞多少 → 直接决定 Agent 表现。**

这揭示了一个重要事实：所谓「Agent 工程」，本质上是**上下文工程**——如何高效地组织和填充 LLM 的上下文窗口。

## 上下文窗口的约束

- 上下文 = 输入问题 + 对话历史 + 系统背景设定（System Prompt）
- 主流窗口大小：128K ~ 1M token
- 超出窗口的内容被压缩或丢弃（「失忆」）
- **最佳实践**：一个上下文窗口只聚焦一个问题，新问题重新开窗口

## Agent 工程的差异

以 Claude Code 为例，它比 Cursor 等 API 调用方式效果更好的关键原因：

- Claude Code 敢给模型塞更多上下文，获取充分信息后再执行
- API 调用受成本限制，倾向于塞更少上下文尽快给答案
- **同样能力的模型，上下文填充策略不同 → 效果差距巨大**

## 换个方向看：不是「塞多少」，而是「谁有写权限」

上面这套「本质都是往窗口里塞信息」的框架，容易把上下文工程读成一道**填充量**问题——塞得够多够全就好。放到多步 Agent 的闭环里，这个直觉会翻面：真正决定成败的不是塞多少，而是**错误信息能不能拿到写权限**。[[2026-07-20-react-agent-error-compounding]]

单步问答里一次预测错了，损失停在那一步；[[react-agent]] 循环里 `Action` 会改写外部世界、选择下一条数据，`Observation` 被截断摘要后回灌进 `Context`，于是**一个早期小偏差会改变后续每一步看到的世界**，沿闭环自激放大。此时窗口里多塞的每一段未标来源的推断、每一次被压成「已确认」的猜测，都不是「信息更全」，而是给错误发了一张长期居留证。所以上下文工程的对象不是 token 数量，而是**什么信息以什么证据等级、什么生命周期进入下一轮决策**。

据此，它落地成分布在回路各接口的一组「写权限闸门」，而非一句更好的 system prompt：

| 接口 | 拦的是 | 手段 |
|------|--------|------|
| 动作前 | Thought→Action 的翻译误差 | 自由文本压成 typed schema + 参数/副作用/权限校验，写操作先 dry-run，参数带实体 ID 而非易混名字 |
| 观察入窗前 | Observation 的测量污染与来源漂白 | 区分 `empty/timeout/permission_denied/parse_error`，原始证据与摘要并存且摘要指回 source span，外部文本按不可信数据隔离、不给指令权 |
| 历史压缩时 | Context 里「猜测升格为事实」 | 用分栏账本拆开 Goal / Facts(带 source) / Hypotheses / Plan / Failures，别让一段自然语言摘要背所有状态 |
| 循环过程中 | 错误的自我复制 | loop detector、按错误类型分配重试预算、无信息观察后强制换查询/工具、checkpoint 重规划而非续喂脏轨迹 |
| 提交前 | 「内部自洽」被误当「外部正确」 | 可执行断言（数字能否定位 source span、实体 ID 是否全程一致）而非同分布的「请再检查一遍」|

一个由此推出的判据：**上下文压缩 vs 精确填充的 trade-off**（见下方开放问题）本质是「压缩会不会顺手把『未验证』压成『已确认』」——压缩不是无损缩短，而是一次改写记忆的机会，最危险的丢失不是丢 token，而是丢证据等级。闭环最终收敛还是发散，取决于三个变量：**observability**（错误在反馈里是否留下可辨信号）、**diagnosability**（能否区分无结果/工具故障/参数错/假设错）、**recoverability**（识别后有无回退换路）——三者弱时，往窗口里多塞一轮反思只是给错误更多自我解释的机会。

## 与相关概念的关系

- [[chain-of-thought]]：CoT 是上下文工程的典型案例——让模型在上下文中写推理草稿
- [[react-agent]]：ReAct 循环中每一步都在往上下文追加内容
- [[tool-use]]：工具描述和调用结果都占用上下文空间
- [[agent-skills]]：Skills 文档需要按需加载到上下文中（渐进式披露）
