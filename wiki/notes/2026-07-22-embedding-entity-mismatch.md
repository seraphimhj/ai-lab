# 伴读：Embedding 为什么会认错实体？

> 本次命中：**RAG / 检索 / Embedding 主线**；补的是“专名、型号、数字这类低频但高信息 token，在 dense 单向量检索里为什么容易丢，以及如何从检索、交互、训练三处补回来”。

## 全局地图

### 一句话摘要

Embedding 认错实体，根因通常不是模型“不认识这个名字”，而是系统把整段文本压成一个相似度时，**话题相似**压过了**身份差异**；hybrid exact-match、late interaction 和 entity-aware 难负例，分别从词表层、匹配层和训练目标层把身份信号补回来。

### 结构地图

```text
输入文本
  |
  +-> tokenizer / encoder
  |       |
  |       +-> 实体信号是否已被上下文稀释？
  |
  +-> pooling 成单向量
  |       |
  |       +-> 一个点能否同时保存话题、实体、数字、关系？
  |
  +-> cosine / dot-product 排序
          |
          +-> 训练是否教过模型：只换实体就必须降分？

三条补救路径
  |
  +-> 稀疏 exact-match：保住字面身份
  +-> late interaction：保住 token 级匹配
  +-> entity-aware hard negatives：教会 dense 模型重视身份变化
```

### 段落分类概览（Agent 判断）

- `[骨]` 误判发生在哪里：从“理解文本”到“压成一个分数”的信息竞争
- `[肌]` 一个实体替换的最小案例
- `[骨]` 修法一：hybrid sparse / dense，把字面身份接回排序
- `[骨]` 修法二：late interaction，不让实体 token 过早消失
- `[骨]` 修法三：entity-aware 难负例，改写模型的相似性边界
- `[肌]` 三种方法的诊断与选择
- `[骨]` 更深一层：实体 mismatch 本质上是任务不变量定义错了

## 逐段伴读

## 1. `[骨]` 模型错的往往不是“语义”，而是“检索任务里的语义”

先看一个查询：

> `A 公司 2025 年营收是多少？`

候选文档有两篇：

- D1：`B 公司发布 2025 年财报，全年营收……`
- D2：`A 公司发布 2024 年财报，全年营收……`

如果你问人“哪篇话题更像”，D1 和查询高度相似：公司、年份、财报、营收全都对，只错了实体。D2 则实体对，但年份错了。

这暴露出一个关键区别：

- **semantic similarity（语义相似）**：两段话在谈相近的事情。
- **retrieval relevance（检索相关性）**：这段话能不能回答这个具体查询。

Dense embedding 常被训练成前者，却被系统拿来近似后者。于是，模型把 D1 排高，不一定是它没看到 A/B 的差异；也可能是训练目标告诉它：共享“公司财报营收”这个主题，比专名变化更重要。

### 结构标注

核心论点：先把“模型不认识实体”的表象，改写成“训练出来的相似性与当前任务的相关性不一致”。

### 注疏：别把锅全甩给 mean pooling

常见解释是：“mean pooling 把实体 token 平均掉了。”这有道理，但不完整。

并非所有 dense encoder 都用 mean pooling；有些取 `[CLS]`，有些用 learned pooling。即使用 mean pooling，也不是机械地把每个 token 等权相加，因为每个 token 的 contextual embedding（上下文化表示）已经通过 attention 混入整句信息。

真正稳定的说法是：

> **单向量瓶颈（single-vector bottleneck）要求模型把多个可能冲突的信号——话题、实体、时间、数字、关系——压进一个固定维度的点，再用一个全局相似度完成排序。训练中哪个信号更能降低 loss，哪个就更容易主导这个点。**

因此，问题可能在四处发生：

```text
tokenization -> contextual encoding -> pooling -> similarity objective
     |                 |               |              |
实体被切碎       实体受上下文稀释    压缩时竞争     loss 不惩罚换实体
```

### 碰撞问题

**“只换一个实体，向量就应该大幅移动”是否永远正确？**

不正确。如果任务是新闻聚类，`A 公司收购 C 公司` 与 `B 公司收购 C 公司` 也许应该靠近；如果任务是回答“A 公司收购了谁”，它们就必须拉开。

所以实体 mismatch 的第一层诊断不是“模型够不够强”，而是：**你的任务把实体变化定义成了应当保持不变的扰动，还是必须改变答案的扰动？**

## 2. `[肌]` 错误是怎么穿过编码链的

把查询简化为：

> `A 公司 营收`

模型可能学出两个主要方向：

- 一个强烈的“公司财务/营收”方向；
- 一个较弱的“A 公司身份”方向。

候选 `B 公司 营收` 与查询共享第一方向，只在第二方向不同。若最终 cosine similarity（余弦相似度）主要由第一方向决定，B 公司就会成为危险负例。

为什么身份方向容易弱？

1. **训练频率不对称**：财报、营收等关系词在大量样本中反复提供稳定梯度；长尾实体出现少。
2. **负例太容易**：若负例是体育新闻，模型只学会区分话题，根本不需要分清同行公司的名字。
3. **池化和归一化压缩**：多个信号最后共用一个向量、一个分数，局部差异没有独立的匹配通道。
4. **标注本身含混**：通用语义相似数据可能认为换实体后句子仍“很像”，但问答检索要求它们“不相关”。
5. **ANN 只执行已有几何**：近似最近邻索引可以引入召回误差，但它通常不会凭空创造实体盲区；它只是忠实执行 embedding 已经学出的空间。

### 结构标注

证据铺垫：实体信号不是在某一瞬间神秘消失，而是在数据、目标、压缩和排序组成的链条中逐渐失去话语权。

以上 1 段在支持骨架段 1 的论证。

## 3. `[骨]` 修法一：hybrid exact-match，在词表层保住身份

Hybrid retrieval（混合检索）通常同时计算：

```text
final_score = alpha * dense_score + beta * sparse_score
```

这里不是要背系数，而是要看两类分数各自保留了什么：

- dense score：擅长同义改写、语义近邻、表达变化；
- sparse score：擅长专名、型号、代码、数字等字面锚点。

BM25 直接利用词项匹配。SPLADE 则把上下文语义投回词表空间：输入里即使没出现某个词，模型也可能点亮相关词项；但结果仍是可按词项索引的稀疏表示。对于实体检索，它们提供了一条 dense 单向量之外的“身份通道”。

### 它补的是哪一环？

```text
单向量语义通道 ------------------+
                                  +-> 分数融合 -> 排序
词项 / exact-match 身份通道 ------+
```

它没有强迫 dense 向量承担所有责任，而是在排序阶段加入另一个归纳偏置：**某些字面重合不只是表面相似，而是相关性的必要条件。**

### 最强反驳

“实体有别名、缩写、旧名、音译，只做 exact-match 不就漏了吗？”

对。这正是要 hybrid 而不是只用 BM25 的原因。exact-match 对 `IBM` 与 `International Business Machines`、`GPT-4o` 与常见误写、中文名与英文名并不天然鲁棒。实践中还需要实体规范化、别名表，或让 dense 通道承担召回改写的职责。

**适合优先使用的场景**：商品型号、公司名、人名、药名、错误码、合同编号，以及“一个字符不同就可能是另一对象”的语料。

### 结构标注

第一种解法：不改 dense 模型，先在检索系统层增加身份信号，成本最低、可解释性最强。

## 4. `[骨]` 修法二：late interaction，把交互推迟到 token 级

Dense bi-encoder 的典型做法是：

```text
query -> 一个向量 q
 doc  -> 一个向量 d
score -> sim(q, d)
```

ColBERT 类 late interaction（后期交互）保留 query 和 document 的多个 token 向量。其核心 MaxSim 可以直观写成：

```text
对 query 的每个 token：
    在 document 的所有 token 中找最高相似度
最后把这些最高分相加
```

简式：

```text
score(q, d) = sum_i max_j sim(q_i, d_j)
```

这意味着查询中的实体 token 不必先和“营收、年份、公司”等其他 token 熔成一个点。它可以独立追问：**文档里有没有一个 token 与我这个实体高度匹配？**

### 为什么它能缓解实体 mismatch？

比较两种压缩时机：

```text
Dense single-vector:
所有 token -> 先压缩 -> 再匹配

Late interaction:
所有 token -> 分别保留 -> 检索时逐 token 匹配 -> 再汇总
```

late interaction 把信息损失推迟了。实体、型号和数字因此拥有单独影响总分的机会。

### 代价

- 每篇文档要存多个 token 向量，存储显著增加；
- 检索和重排比单向量 MIPS 更复杂；
- MaxSim 仍不等于完整 cross-encoder，它保留细粒度匹配，但没有在查询和文档之间重新跑全部 attention；
- tokenizer 若把罕见实体切得很碎，实体信号仍可能不稳定。

因此它常作为“精度更高但更贵”的召回或重排层，而不是无条件替代单向量检索。

### 结构标注

第二种解法：改变表示与匹配架构，让实体 token 在最终打分前保持独立。

## 5. `[骨]` 修法三：entity-aware 难负例，让“换实体”真正产生梯度

假设训练样本是：

- query：`A 公司 2025 年营收`
- positive：A 公司 2025 年财报
- easy negative：某场足球比赛报道
- entity-hard negative：B 公司 2025 年财报

只用 easy negative，模型学会“财报比足球更相关”就能把 loss 降得很好。它没有动力学习 A 与 B 的差异。

加入 entity-aware hard negative（实体感知难负例）后，话题、句式、年份、关系几乎都被控制住了，**唯一可靠的判别特征就是实体身份**。此时 InfoNCE / softmax 对比损失才会把梯度压到真正的薄弱处：

```text
希望：score(query, A-company-doc)
      > score(query, B-company-doc)
```

这和实验设计中的“控制变量”是同一个形状：让正负样本只在待学习因素上变化，模型才不能靠旁门左道答对。

### 难负例怎么造？

1. **实体替换**：保持句法和关系不变，把主体或客体换成同类型实体。
2. **同槽位挖掘**：从同产业、同产品族、同姓人名中找近邻。
3. **当前模型挖掘**：取 dense 模型排名靠前但实体不匹配的结果，再经过规则或标注过滤。
4. **关系约束**：不仅实体同类型，还要让关系上下文相似，例如都谈“营收”而不是一个谈营收、一个谈创始人。

### 最危险的坑：false negative

如果 B 公司文档里恰好也提到了 A 公司，或者查询本来允许类别答案，那么这个“负例”可能实际相关。错误难负例会教模型排斥真正答案。

所以难负例不是越难越好，而是：

> **在业务相关性定义下确实为负，同时尽可能消除实体之外的捷径。**

### 结构标注

第三种解法：不增加在线匹配结构，而是通过训练数据重新规定“相似”和“相关”的边界。

## 6. `[肌]` 三种修法不是三选一，而是三个拦截点

| 观察到的错误 | 先查什么 | 优先修法 | 原因 |
|---|---|---|---|
| 专名、型号、错误码经常被相近主题覆盖 | 字面命中是否能区分答案 | BM25/SPLADE hybrid | 最快补回身份锚点 |
| 长查询里多个实体、属性分别需要对齐 | 单向量是否过早压缩 | late interaction | 每个 query token 有独立匹配机会 |
| 模型总把同行、同类产品互相混淆 | 训练负例是否只区分了话题 | entity-aware hard negatives | 迫使模型学习“换实体即负” |
| 别名、缩写、音译造成漏召回 | 实体规范化是否缺失 | alias normalization + hybrid | 单纯 exact-match 无法跨别名 |
| 精排能纠正，但召回阶段根本没取到正确文档 | top-k 候选中是否存在正确答案 | 改召回，不只改 reranker | 精排无法救回未召回文档 |

一个务实的系统组合通常是：

```text
query
  |
  +-> dense retrieval --------+
  |                            |
  +-> sparse retrieval -------+-> union / fusion
                                   |
                                   +-> token-level or cross-encoder rerank
                                   |
                                   +-> answer generation
```

训练侧再持续把线上出现的实体混淆转成高质量 hard negatives，形成反馈闭环。

### 结构标注

实践归纳：三种方法分别改“候选从哪来”“分数怎么算”“模型学什么”，可以叠加而非互斥。

以上 1 段在支持骨架段 3、4、5 的论证。

## 7. `[骨]` 更深一层：这是“不变量”定义错误

Embedding 训练一直在回答一个隐含问题：

> 什么变化发生后，文本仍应被视为“相同”？什么变化必须让它们分开？

在图像对比学习里，裁剪、颜色扰动常被设成不改变图像身份的 augmentation（数据增强）。在检索里，同义改写往往也应保持相关性。但**实体替换并不是普遍安全的增强**：

- `A 公司收入` -> `A 企业营收`：表达变了，答案对象没变，应该接近。
- `A 公司收入` -> `B 公司收入`：表达几乎没变，答案对象变了，在实体检索中必须分开。

表面改动更小，任务含义反而变化更大。这正是 entity mismatch 难学的地方：语言模型天然擅长捕捉大面积共享语义，而业务相关性可能由一个很短的 token 决定。

### 旁逸：它和因果推断是同一个形状

实体难负例近似一个最小干预：保持年份、关系、句式不变，只替换实体，然后观察相关性标签是否翻转。

```text
原样本：entity=A, context=C -> relevant
干预后：entity=B, context=C -> irrelevant
```

如果模型预测没有随这个干预改变，说明它依赖的是 context C，而不是决定答案的实体。这比看 attention 热力图更直接：你不是问模型“看了哪里”，而是在测试“改变哪里会改变结论”。

### 最终判断

所以，解决实体 mismatch 的优先顺序不应是“先换更大的 embedding 模型”，而应是：

1. 定义业务上哪些实体变化必须改变相关性；
2. 建一个 entity-swap 切片评测集；
3. 判断正确答案是在召回前丢失，还是排序时被压低；
4. 在对应环节加入 sparse 身份通道、token 级交互或实体难负例；
5. 再评估总体召回与实体切片是否同时改善。

### 结构标注

终局论点：实体 mismatch 不是孤立的模型缺陷，而是“任务相关性如何编码进数据、表示和排序”的闭环问题。

## 全文复盘

### 理解轨迹

```text
“mean pooling 把名字平均掉了”
             |
             v
“单向量 + 训练目标让话题信号压过身份信号”
             |
             v
“在词表层、匹配层、训练层分别补回实体身份”
             |
             v
“先定义：实体替换在当前任务中是否必须改变相关性”
```

### 三句话带走

1. **Dense embedding 优化出的“相似”，不自动等于业务需要的“相关”。**
2. **Hybrid、late interaction、entity-aware hard negatives 分别保身份、保 token、改边界。**
3. **先做实体替换切片评测，再决定修召回、修交互还是修训练；不要先盲目换大模型。**

### 读后一句话（不可跳过）

读完后，请只回答一句：

> **如果只能改一处，你当前系统的实体 mismatch 更像是“候选没召回”“单向量打分压错了”，还是“训练从未教过模型实体变化很重要”？为什么？**

### 终局问题

如果同一个实体在不同任务里有时应该成为强边界、有时又应该被忽略，那么我们是否还该期待一个固定的通用 embedding 空间，同时服务问答检索、聚类、推荐和去重？还是“相似性”本来就必须由任务条件化？

### 术语表

| 英文 | 中文 | 本文含义 | 出现位置 |
|---|---|---|---|
| semantic similarity | 语义相似 | 两段文本谈论内容接近 | 第 1 节 |
| retrieval relevance | 检索相关性 | 文档能否满足具体查询 | 第 1 节 |
| single-vector bottleneck | 单向量瓶颈 | 多种信号被压进一个向量和一个总分 | 第 1 节 |
| exact match | 精确字面匹配 | 通过实体、型号等词项重合保住身份 | 第 3 节 |
| hybrid retrieval | 混合检索 | 融合 dense 与 sparse 检索结果 | 第 3 节 |
| late interaction | 后期交互 | 保留 token 向量，到检索时才逐 token 匹配 | 第 4 节 |
| MaxSim | 最大相似度聚合 | 每个查询 token 找文档中最相似 token，再汇总 | 第 4 节 |
| entity-aware hard negative | 实体感知难负例 | 话题相似但关键实体不同的负样本 | 第 5 节 |
| false negative | 假负例 | 被标成负样本、实际却相关的文档 | 第 5 节 |
| invariance | 不变量 | 哪些输入变化不应改变模型判断 | 第 7 节 |

### 下一步线索

下一步最值得接的是 **ColBERT 的 MaxSim 与 MUVERA 的 Fixed Dimensional Encoding**：今天只说明了“为什么保留 token 向量能救实体”，下一步可以继续追问——多向量表示的存储账有多贵，以及 MUVERA 如何把多向量检索近似塌回固定维向量，同时尽量保留 late interaction 的优势。
