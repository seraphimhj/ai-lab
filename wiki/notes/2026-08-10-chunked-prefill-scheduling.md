# 伴读：长 Prompt 为什么会堵住整张卡？——Chunked Prefill 与推理调度的队头阻塞

> 本次命中：*retrieval 以外·推理系统薄弱点 + Agent / 上下文工程主线 + 端到端闭环*。昨天讲 Prefix Caching 如何避免重复 prefill；今天推进到缓存未命中之后：即使总算力足够，一个超长上下文也可能因为调度粒度不对，让所有短请求一起变慢。

## 全局地图

### 一句话摘要

Chunked Prefill 把长输入的预填充切成可调度的小块，使调度器能在块与块之间插入正在解码的请求；它解决的不是总计算量，而是长 prefill 独占 GPU 引起的队头阻塞，并把吞吐、首 token 延迟和逐 token 延迟放进同一张预算表。

### 结构地图

```text
一个 GPU 上混合了两类工作

Prefill:  一次处理很多输入 token，算力密集，可并行
Decode:   每条序列每轮只前进一步，带宽敏感，怕等待
                |
                v
朴素调度: [--------- long prefill ---------][D][D][D]...
                |
                `-- decode 请求长时间得不到服务

分块调度: [chunk][D][chunk][D][D][chunk][D]...
                |
                +-- 长 prompt 仍被完整计算
                +-- 但不再长时间独占调度周期
                `-- 每轮 token 预算决定延迟与吞吐的交换

三层判断:
算了多少?        总工作量
何时得到算力?    调度公平性
算力如何组合?    prefill/decode 混批效率
```

### 段落分类（Agent 判断，可覆盖）

## 逐段伴读

## 1. [骨] Prefill 和 decode 看似都在跑 Transformer，脾气却不一样

一次生成请求可以拆成两个阶段。

*Prefill（预填充）*读取整段输入，建立每层的 KV 状态，并算出首个输出 token。一个 20K token 的 prompt，通常能把大量 token 组成矩阵运算并行处理，因此更容易吃满 GPU 的计算单元。

*Decode（解码）*每轮为每条序列生成一个新 token。它必须等上一个 token 落地，单条序列很难沿时间维并行；每一步还要读取权重和不断增长的 KV cache，因此常更受内存带宽限制。

粗略地说：

```text
Prefill: 大批输入一起算  -> 较偏 compute-bound
Decode:  每轮前进一步    -> 较偏 memory-bound
```

这不是绝对定律，模型大小、batch、硬件和并行策略都会改变瓶颈；但它足以解释调度难题：*同一张 GPU 同时排着两种资源画像不同、延迟目标也不同的工作。*

Prefill 请求最关心的是 *TTFT（Time To First Token，首 token 延迟）*；已经开始输出的 decode 请求更关心 *ITL（Inter-Token Latency，token 间延迟）*，也就是用户看到文字流是否突然停顿。

*结构标注：核心定义。* 后面的全部权衡都来自 prefill 与 decode 在资源画像和延迟目标上的不对称。

### 碰撞

设一个聊天请求已经开始流式输出，每 40 ms 来一个 token。此时调度器启动一段耗时 800 ms 的长 prefill，并且中途不可让出 GPU。用户看到的不是“这个新请求首 token 慢”，而是*已有请求的输出也会突然卡住约 800 ms*。

所以延迟不是请求自己的私事。共享加速器上，一个请求的形状会进入别人的用户体验。

## 2. [肌] 一个长 Agent 请求，怎样堵住一批短对话？

想象当前 GPU 上有 32 条正在 decode 的会话。每轮调度本可让每条会话各前进一步。此时进来一个带 64K 工具日志和文档的 Agent 请求。

如果调度器把它的整个 prefill 当作不可分割任务：

```text
时间 --->

短请求 decode:  D D D D |.........................| D D D
长请求 prefill:          |PPPPPPPPPPPPPPPPPPPPPPPPP|
                         ^                         ^
                         开始                      完成
```

点线区域里，32 条短请求都在等。即使长请求本身“合理”，它也制造了 *Head-of-Line Blocking（队头阻塞）*：排在队头的大任务阻止后面的短任务获得服务。

这和网络路由器里一个巨型数据包堵住小时延流量、操作系统里一个长任务占满 CPU 时间片，是同一种形状。问题不一定是资源不足，而是*资源让出的最小粒度太大*。

请注意，这与昨天的 Prefix Caching 是两个问题：

- 若 64K 前缀已缓存，很多 prefill 根本不必再算；
- 若缓存没有命中，这 64K 仍要计算，此时才轮到调度器决定是否允许它连续独占 GPU。

*结构标注：场景证据。* 长 prompt 把上下文工程中的长度选择，转化成了共享系统中的延迟外部性。

以上 1 段在支持第一节“混合工作负载需要显式调度”的论证。

## 3. [骨] Chunked Prefill：不减少工作，只缩小不可抢占区间

*Chunked Prefill（分块预填充）*把一段长输入拆成多个 token chunk。调度器处理一块后，保留已经建立的 KV 状态；下一轮可以先服务 decode，再继续下一块。

```text
原输入:
[P1 P2 P3 P4 P5 P6 P7 P8]

整段 prefill:
[P1 P2 P3 P4 P5 P6 P7 P8][decode...]

chunked prefill:
[P1 P2][decode][P3 P4][decode][P5 P6][decode][P7 P8]
```

关键是：P1 到 P8 一个都没有消失。若没有缓存，模型仍需计算全部输入 token。变化发生在*何时算*和*一次连续算多少*。

因此它最像操作系统的时间片，而不是算法复杂度优化：

```text
Prefix caching  -> 删除已经做过且可复用的工作
Chunked prefill -> 把必须做的工作切小，允许交错执行
```

这一区分非常重要。若基准只统计每秒处理了多少总 token，分块甚至可能因为调度和 kernel 边界增加少量开销；但若关注线上 P99 ITL，它可能显著减少“突然停住”的长尾。

这暴露出模型系统常见的指标冲突：*平均吞吐几乎不变，不等于用户体验没有改善；总 FLOPs 没减少，也不等于调度优化没有价值。*

*结构标注：核心机制。* Chunked Prefill 优化的是最大连续占用时间和可调度性，而非省掉 Transformer 层。

### 注疏：它和抢占式多任务是同一个形状

操作系统不要求一个进程从开始一直跑到结束才轮到别人。它把执行切成时间片，用上下文状态保证下次能接着跑。

```text
CPU 调度:  保存进程状态 -> 让出 CPU -> 恢复执行
LLM prefill: 保存已有 KV -> 让出 GPU -> 继续后续 token
```

但两者也有差别：GPU kernel、张量并行通信和批形状重组都有成本，LLM serving 不能假设切得越细越好。粒度太大导致阻塞，粒度太小则把时间花在切换和低效小算子上。

## 4. [骨] 真正的旋钮不是“开不开分块”，而是每轮 token budget

调度器通常需要一份每轮预算：这一轮最多安排多少 token 进入计算。可以把它记作 *token budget*。

假设每轮预算是 2048 token：

1. 先给 512 条 decode 序列各安排 1 个 token，消耗 512；
2. 剩余 1536 可以给一个或多个 prefill chunk；
3. 超出的长 prompt 留到下一轮。

```text
每轮预算 2048

[512 decode tokens][1536 prefill tokens]
|-------------------------------|
            one iteration
```

这里有三方拉扯：

- chunk 太大：prefill 矩阵更大，计算效率通常更好，但 decode 等待更久；
- chunk 太小：decode 更平滑，却可能增加调度开销，让 prefill 吃不满 GPU；
- decode 优先级太高：已有用户很流畅，新请求却迟迟拿不到首 token；
- prefill 优先级太高：新请求较快开始，正在生成的请求却出现抖动。

所以不能只问“Chunked Prefill 是否更快”，而要同时观察三类指标：

```text
TTFT:     新请求等多久才开始输出
ITL/TPOT: 已开始请求的 token 是否连续
Throughput: 单位时间系统完成多少工作
```

还要看 P50、P95、P99，而非只有平均值。队头阻塞最常藏在长尾里：多数短 prompt 表现很好，少数超长 prompt 到来时却让整批请求同时抖一下，平均数会把事故抹平。

*结构标注：核心权衡。* Token budget 把调度策略变成可量化控制问题，而不是一个布尔功能开关。

### 压力测试

如果团队把“总 token/s”设成唯一 KPI，最容易选出哪种策略？

很可能是偏爱大 batch、大 prefill chunk、长时间不打断高效矩阵运算的策略。它在离线吞吐测试中漂亮，却可能牺牲交互式请求的 P99 ITL。

如果反过来只优化最小 ITL，系统又可能用极小 chunk 频繁切换，让长 prompt 的 TTFT 和整体成本恶化。

结论不是折中取一个固定常数，而是：*预算应与服务等级和工作负载分布绑定。* 交互聊天、离线批处理、代码 Agent、长文档摘要不该默认共用同一优先级。

## 5. [肌] 三种优化到底各管哪一笔账？

最近几次伴读可以拼成一张调度地图：

```text
请求到达
   |
   v
是否有相同前缀?
   | yes
   +------> Prefix Caching: 跳过可复用 prefill
   |
   | no / 剩余后缀
   v
输入是否很长?
   |
   +------> Chunked Prefill: 切小并与 decode 交错
   |
   v
进入持续服务循环
   |
   +------> Continuous Batching: 完成者退出，新请求补位
   |
   v
逐 token decode
```

三者分别回答：

| 机制 | 它问的问题 | 它主要拿回什么 |
|---|---|---|
| Prefix Caching | 这段输入以前是否已经算过？ | 重复 prefill 计算 |
| Chunked Prefill | 必须算的长输入能否分段让出资源？ | 队头阻塞与 ITL 长尾 |
| Continuous Batching | batch 中序列完成后能否立即换入新请求？ | 静态 batch 的空泡 |

它们不是替代关系。一个成熟 runtime 可能同时使用三者：先复用缓存，未命中的后缀分块，再把 prefill 与动态变化的 decode batch 一起调度。

*结构标注：概念归位。* 以上 3 种机制共同支持“推理加速不是一个技巧，而是对重复工作、调度粒度和动态容量的分层治理”。

以上 1 段在支持第三、四节的论证。

## 6. [骨] 为什么不能随便从 token 中间切开？

“把输入切块”听起来像字符串分片，但正确实现必须保持一次性 prefill 的模型语义。

对因果语言模型，后面 chunk 中每个 token 必须能注意到前面所有已处理 token。实现需要：

- 保留前面 chunk 产生的每层 KV；
- 使用正确的绝对或相对位置；
- 构造正确的 causal attention 范围；
- 在张量并行、流水线并行下保持各设备状态一致；
- 正确处理不同请求的变长块和 batch 重组。

```text
chunk 1: token 1 ... 1024
              |
              `-- KV retained
                     |
chunk 2: token 1025 ... 2048
         can attend to 1 ... 2048 under causal mask
```

如果 chunk 2 只能看到自己，它就不是同一个模型计算；如果位置从零重新开始，位置编码也变了。Chunked Prefill 必须满足一个基本正确性条件：*在允许的数值误差范围内，分块与整段 prefill 应产生等价的后续生成分布。*

另外，分块不代表 KV 内存压力消失。每处理一块，长请求的 KV 仍继续增长。调度器可能还要面对：

- KV 空间不足，是否抢占或 swap 某请求；
- 一个超长请求占据大量 block，挤出更多短请求；
- prefill 与 decode 混批后，kernel 是否仍高效；
- LoRA、不同模型或不同租户是否能安全混批；
- 取消请求后，已分配的 KV 能否及时回收。

因此分块只解决“长时间不让路”，没有自动解决“长请求占很多内存”和“总容量有限”。

*结构标注：最强限定。* 调度上的可抢占性必须建立在模型语义等价和 KV 生命周期正确之上。

## 7. [骨] 端到端闭环：Prompt 长度不是输入属性，而是系统控制变量

把链条接起来：

```text
Agent 设计
(工具数量、历史保留、RAG 文档、轨迹日志)
        |
        v
输入长度与长度方差
        |
        v
prefill 工作量、KV 占用、缓存命中
        |
        v
chunk 大小、token budget、调度优先级
        |
        v
TTFT、ITL、吞吐、单位请求成本
        |
        v
产品超时与上下文裁剪策略
        |
        `---------------------> 反过来改变 Agent 设计
```

这里最容易漏掉的是*长度方差*。平均 prompt 都是 4K，不代表工作负载温和：

```text
系统 A: 几乎所有请求都是 4K
系统 B: 99% 是 1K，1% 是 301K

两者平均值都可能接近 4K，调度风险完全不同。
```

系统 B 的极少数长请求会同时带来 prefill 长任务、巨量 KV 占用和队头阻塞。若评测只用“平均 4K”的合成请求，就看不见真实线上长尾。

这和此前“平均指标抹掉关键少数信号”的病灶完全同构：

```text
评测端: 平均准确率掩盖失败子集
Serving 端: 平均输入长度掩盖超长请求尾部
```

对应修法也同构：按 slice 看。至少把请求按输入长度、输出长度、是否 cache hit、交互式/批处理、租户或任务类型分层报告。

真正可执行的服务策略可以是：

1. 交互式 decode 保留最低服务份额，避免被长 prefill 饿死；
2. 超长 prefill 强制分块，并按 SLO 设 chunk 上限；
3. 离线长文任务进入单独队列或设备池；
4. 先做 prefix cache 查找，再只对未命中后缀分块；
5. 用真实长度联合分布压测，而不是固定 prompt/output 长度；
6. 同时验 TTFT、ITL、吞吐、KV 占用与取消回收。

最后的原则是：*上下文越长，模型可能知道得越多，但系统并不会只向这个请求收费；共享调度下，长上下文还会把等待成本外溢给别人。*

*结构标注：闭环结论。* 上下文工程决定工作负载形状，调度器把这种形状翻译成所有用户共同承担的延迟。

## 全文复盘

### 理解轨迹

```text
起点: 长 prompt 只是自己的首 token 更慢
  |
  v
第一次转折: 整段 prefill 独占 GPU，会阻塞正在 decode 的请求
  |
  v
机制: Chunked Prefill 保存阶段性 KV，把长任务切成可交错的小块
  |
  v
关键区分: 它不减少总计算，只缩短不可让出的连续区间
  |
  v
调度权衡: token budget 同时牵动 TTFT、ITL 和吞吐
  |
  v
最强限定: 分块必须保持位置、注意力和 KV 生命周期正确
  |
  v
终点: Prompt 长度分布决定 serving 架构，也给其他请求制造外部性
```

### 读后一句话

请在心里完成这句；这是今天唯一不要快进的部分：

> “当平均 token/s 没有明显提升，但 P99 ITL 因 Chunked Prefill 大幅下降时，我会判断这项优化 ________，因为它改变的是 ________，而不是 ________。”

达到 L2 的回答不会只说“用户体验更好”，而会明确区分：它改善了长 prefill 下的调度阻塞和服务公平性，并未声称删掉全部输入计算。

### 终局问题

如果超长上下文能提高单个 Agent 的成功率，却会占用更多 KV、拖慢同机其他用户，那么：*“允许一个请求使用多长上下文”应该由模型能力决定、由付费等级决定，还是由它给共享系统造成的边际外部成本决定？*
