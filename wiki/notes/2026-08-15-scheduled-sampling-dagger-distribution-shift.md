# 从 Teacher Forcing 到 DAgger：为什么“偶尔喂模型自己的答案”仍可能学错

> 本次命中：*端到端闭环 + 统一数学框架 + Agent / 上下文工程*。承接昨天的 exposure bias，今天补上更尖锐的一层：训练分布与上线分布不同，不只是“误差会累积”，还会让一个看似合理的训练目标失去统计一致性。

## 全局地图

### 一句话摘要

Teacher Forcing 的根病不是模型没见过错误，而是训练时由专家历史决定“去哪里看”；Scheduled Sampling 试图混入模型历史，却可能教会模型忽略历史；DAgger 真正修正的是*状态分布*：让当前策略决定去哪里，再向专家询问那里应该怎么做。

### 结构地图

```text
Teacher Forcing
  训练访问：专家历史产生的状态
  上线访问：模型历史产生的状态
             |
             v
       covariate shift
       协变量偏移
             |
       +-----+------------------+
       |                        |
       v                        v
Scheduled Sampling           DAgger
混合“正确/模型 token”         用当前策略采状态
但目标仍按局部 token 拼接      再让专家标注动作
       |                        |
       v                        v
可能破坏条件依赖              聚合数据，反复重训
“历史不可信，干脆忽略”         训练分布追上部署分布
```

### 段落分类概览（Agent 判断，可覆盖）

- [骨] 病灶重述：问题是状态分布错位，不只是单步准确率不足
- [肌] 一个两步反例：为什么 Scheduled Sampling 会学会忽略前文

- [筋] 从序列生成过渡到 Agent 工具调用
- [骨] 工程落点：什么时候该改数据，什么时候该改策略，什么时候该加护栏

## 1. [骨] 真正错位的是“模型在哪里犯错”

昨天我们说，Teacher Forcing（教师强制）训练第 t 步时，总把真实前缀交给模型：

```text
训练：p_data(y_<t) 产生历史，再学 p_theta(y_t | y_<t)
上线：p_theta(y_<t) 产生历史，再用 p_theta(y_t | y_<t)
```

表面上，两边都在预测“下一个 token”；实际上，条件里的历史来自两个不同分布。

- 训练只问：在*专家走过的状态*上，你会不会做下一步？
- 上线却问：在*你自己造成的状态*上，你还能不能继续？

这就是 covariate shift（协变量偏移）：输入分布变了，但我们仍希望同一个条件策略有效。这里的“输入”不是静态样本，而是模型自己一步步制造出来的历史。

一个关键区别：

```text
普通监督学习：预测错了，不会改变下一条测试样本
自回归 / Agent：预测错了，会改变下一步将看到的输入
```

所以误差不是只在输出端累积；它还在*数据生成机制*里回流，重新塑造后续输入分布。

*结构标注：核心论点。把 exposure bias 从“现象描述”提升为“状态分布错位”。*

### 碰撞一

作者最想让你接受的点不是“模型会犯错”，而是：

> *The learner changes the distribution of states it will later be tested on.*  
> 学习者会亲手改变自己之后接受测试的状态分布。

暂停十秒想一下：如果某一步的错误不会改变后续输入，它还属于这里讨论的 exposure bias 吗？

答案倾向于“不属于”。那更像普通的独立误差；闭环问题的关键是*行动改变了未来观测*。

## 2. [肌] Scheduled Sampling 为什么直觉正确，却可能目标错误

Scheduled Sampling（计划采样）的直觉很自然：训练时不要永远喂真实 token，偶尔喂模型上一步自己生成的 token，让它提前适应上线环境。

```text
第 t 步训练输入：
  以概率 epsilon 使用真实 y_(t-1)
  以概率 1-epsilon 使用模型生成的 yhat_(t-1)
```

随着训练推进，逐渐降低 epsilon。它看起来在缩短 train-test gap（训练—测试鸿沟）。但问题在于：*被喂进来的 token 来自模型，监督标签却仍来自原始正确序列。* 两者可能已经不属于同一个条件世界。

看一个极小的两步序列。数据只包含两种合法序列：

```text
A -> X
B -> Y
```

第一步 A 或 B 各占一半；第二步完全由第一步决定：看到 A 就应预测 X，看到 B 就应预测 Y。

现在 Scheduled Sampling 在第二步训练时，可能把模型自己采出的 B 当作前缀，却仍拿原样本的 X 当标签：

```text
输入前缀：B
训练标签：X
```

同理也可能出现：

```text
输入前缀：A
训练标签：Y
```

如果这种错配足够多，最安全的学习策略是什么？不是更认真地利用前缀，而是*认为前缀不可靠，逐渐忽略它*，把 X 和 Y 都预测成边缘分布的一半一半。

这正是 Scheduled Sampling 的深层风险：它本来想教模型“错误历史下如何恢复”，却可能通过不一致的标签教模型“历史与未来没关系”。

*结构标注：反例证据。说明“让模型看自己的输出”并不自动等于修正部署分布。*

### 注疏：proper scoring rule 的侧光

昨天之前我们讲过 proper scoring rules（恰当评分规则）：如果样本确实来自目标条件分布，最小化 NLL 会鼓励模型诚实报告那个分布。

但 Scheduled Sampling 改造了条件输入，却没有同步改造标签生成过程。此时 NLL 本身没有坏；坏的是你交给 NLL 的“条件—标签”配对不再代表想学习的联合分布。

```text
损失函数正确 + 数据联合分布错误 = 仍会学错
```

这把“统一数学框架”再推进一步：不要只问 loss 是不是交叉熵，还要问*期望是对哪个分布取的*。

“以上反例与注疏在支持骨架段 1：问题的核心是训练分布，而非只在输入里掺多少模型 token。”

## 3. [骨] DAgger 修的不是 token，而是访问状态的分布

DAgger 是 Dataset Aggregation（数据集聚合）的缩写，来自模仿学习。它面对的问题与自回归生成同形：专家示范的数据只覆盖专家会访问的状态；学习策略稍有偏差，就会进入专家演示里没有的状态。

它的循环不是“在专家轨迹里掺一点模型动作”，而是：

```text
1. 用当前策略 pi_i 真正跑一遍任务
2. 收集 pi_i 实际访问到的状态 s
3. 对每个状态，向专家 pi_star 询问正确动作 a_star
4. 把 (s, a_star) 加入聚合数据集 D
5. 在整个 D 上重新训练，得到 pi_(i+1)
6. 重复
```

最重要的是第 2、3 步的配对：

- *状态来自学习者*：覆盖部署时真的会去到哪里
- *标签来自专家*：告诉学习者在那个状态怎样恢复或继续

与 Scheduled Sampling 的差别可以压成一行：

```text
Scheduled Sampling：模型造前缀 + 原轨迹的下一 token
DAgger：模型造状态   + 专家针对该状态重新给动作
```

前者可能把不相容的前缀和标签缝在一起；后者要求专家标签与当前状态语义一致。

从目标函数看，普通行为克隆近似优化：

```text
E_(s ~ d_expert) [ loss(pi(s), pi_star(s)) ]
```

DAgger 则想逼近：

```text
E_(s ~ d_pi) [ loss(pi(s), pi_star(s)) ]
```

其中 d_expert 是专家策略诱导的状态分布，d_pi 是学习策略自己诱导的状态分布。*loss 可能完全没变，变的是外层期望中的采样分布。*

这与近期几篇伴读的同构关系非常强：

```text
DoReMi / 难负例 / Importance Sampling：改“哪些样本获得梯度”
DAgger：                         改“哪些状态获得专家梯度”
```

训练目标不只由每个样本的损失定义，还由谁有机会成为样本定义。

*结构标注：解决方案骨架。将闭环偏移改写成外层采样分布问题。*

### 碰撞二：最强反驳

如果你接受 DAgger，一个强反驳是：

> “语言生成不存在一个能对任意错误前缀给出唯一正确下一 token 的专家。错误前缀可能已经让原答案失效，甚至没有可恢复路径。”

这个反驳成立。DAgger 的思想可以迁移，但不能把算法原封不动搬到所有语言任务。关键障碍是 expert query（专家查询）：谁来给模型自己造成的任意状态重新标注？

可能的近似包括：

- 可验证任务：用执行器、单元测试、环境反馈当专家
- Agent 任务：让高质量轨迹生成器针对当前环境状态重新规划
- 对话任务：收集人类对真实失败上下文的恢复示范
- 纯开放生成：很难定义唯一专家动作，DAgger 化会更弱、更昂贵

所以 DAgger 不是“Scheduled Sampling 的万能替代”，而是一把诊断尺：*如果你改变了输入状态，却不能为新状态提供语义一致的标签，就要怀疑训练信号。*

## 5. [骨] Agent 场景里，DAgger 比在开放文本里更落地

Agent 的状态通常不只是文本前缀，而是：

```text
s_t = 当前页面 / 文件 / 数据库状态
    + 已执行工具及返回值
    + 权限与预算
    + 上下文里的已有判断
```

动作则是下一次 tool call、参数或终止决定。Agent 执行错误动作后，环境可能真的被改变：文件已移动、表单已提交、数据库返回了意外结果。此时再拿“完美轨迹的下一步”监督，往往答非所问。

一个具体例子：

```text
专家轨迹：
  搜索订单 -> 找到唯一订单 -> 退款

模型轨迹：
  搜索订单 -> 搜索条件过宽，得到三个同名订单
```

如果训练仍把原轨迹的“退款订单 #123”硬接在“三个候选订单”的状态后面，模型学到的不是恢复能力，而是忽略观察、照抄剧本。

DAgger 式数据应当重新询问专家：在“三个候选订单”这个真实状态下该做什么？专家动作可能变成：

```text
向用户确认订单日期，或调用详情工具消歧；禁止直接退款。
```

这正好解释了为什么高质量 Agent 数据不能只有成功轨迹，还需要 *recovery trajectories（恢复轨迹）*：

- 参数错误后如何读取错误信息并修正
- 检索出多个候选后如何消歧
- 权限不足后如何降级，而不是重复调用
- 证据冲突时如何停止并请求确认
- 已产生副作用后如何核验、补偿或升级人工

*结构标注：应用骨架。把 DAgger 的“当前策略状态 + 专家重标”落到工具闭环。*

### 旁逸：它和 SRE 故障演练是同一个形状

只在正常流量上训练 Agent，像只在系统健康时写 runbook；真正缺失的是故障状态下的动作标签。Chaos Engineering 主动制造故障，不是为了增加“坏数据”，而是为了让团队和系统访问平时见不到、上线一定会遇到的状态，再为这些状态形成恢复策略。

```text
DAgger：当前策略访问陌生状态 -> 专家标恢复动作
故障演练：系统进入异常状态     -> runbook 标恢复动作
```

两者都在补“正常轨迹没有覆盖的状态空间”。

## 6. 工程判断：三种问题不要混成一种药

### 6.1 状态没覆盖：改数据采集

信号：模型在专家轨迹上准确，但一旦偏离就完全不会恢复。

做法：on-policy rollout、失败回放、恢复轨迹、DAgger 式重标。重点是让训练集覆盖模型实际访问的状态。

### 6.2 标签与新状态不一致：改标注协议

信号：把模型输出混入上下文后，仍沿用原轨迹标签；模型越来越不看观察或历史。

做法：对新状态重新标注，不要机械继承原序列下一步。无法可靠重标时，宁可承认该任务不适合简单 Scheduled Sampling。

### 6.3 错误动作不可安全探索：加护栏，不靠训练硬扛

信号：一次错误会产生不可逆副作用，例如付款、删除、发信、改权限。

做法：沙箱、dry-run、幂等键、权限分层、执行前验证器、人工确认。DAgger 需要“让当前策略跑”，但不意味着允许它在生产环境自由制造灾难。

```text
数据修复：让模型见过残局
目标修复：让残局与标签一致
系统护栏：让学习代价可承受
```

*结构标注：决策框架。区分分布、监督和安全三层问题。*

### 终局问题

> 当 Agent 的一个动作会不可逆地改变环境时，我们既需要 on-policy 数据覆盖真实状态，又不能让它自由探索危险状态——*怎样设计一种“足够像上线、但失败代价有上限”的状态分布？*

这不是单纯的数据问题。它把模拟器保真度、权限设计、反事实评估和人类监督接到了一起。
