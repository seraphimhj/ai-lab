# 伴读：上下文工程如何拦住 Agent 的误差复合

> 本次命中：**端到端闭环·偏差传导 + Agent / 工具使用 / 上下文工程主线**；承接 07-20 的 ReAct 误差复合，今天不再问“误差从哪来”，而问“观察进入下一轮上下文之前，哪里能装保险丝”。

材料：主题式讲解，围绕四种工程模式展开：**compaction（压缩）/ 子代理隔离 / 按需检索 / 外部记忆**。

## 全局地图

### 一句话摘要

上下文工程不是把更多内容塞进窗口，而是在 Agent 的“观察 -> 下一步输入”边界上管理信息的**进入、传播、保留与淘汰**：四种手段分别对付噪声累积、污染扩散、窗口争抢和状态丢失，但每一种都会引入新的信息损失或协调风险。

### 结构地图

```text
ReAct 闭环

目标 -> 推理 -> 行动 -> 观察 -> 写入上下文 -> 下一轮推理
                         |
                         +-- 原样累积: 噪声、旧假设、工具回显一起回灌

四道不同的保险丝

观察 --[compaction]------> 只保留决策、证据、未决事项
  |
  +----[子代理隔离]------> 局部探索留在局部，只交付结构化结果
  |
  +----[按需检索]--------> 大材料默认不入窗，需要时才展开
  |
  +----[外部记忆]--------> 跨轮状态写到窗口外，按规则读回

它们切的不是同一类故障

compaction   : 挡噪声随轮数增长
子代理隔离   : 挡局部错误横向扩散
按需检索     : 挡无关材料抢占注意力
外部记忆     : 挡超窗后关键状态消失
```

### 段落分类概览（Agent 判断）

- [骨] 上下文不是聊天记录，而是 Agent 下一步决策的可变状态。
- [骨] Compaction：缩短历史，但真正难点是决定哪些信息不可逆地丢弃。
- [骨] 子代理隔离：用上下文边界限制污染半径，但 handoff 会成为新瓶颈。
- [骨] 按需检索：把“拥有信息”改成“拥有取回信息的能力”。
- [骨] 外部记忆：把工作记忆和持久状态分离，但写入策略比存储介质更重要。
- [肌] 四招如何组合成一条可落地的控制链。
- [骨] 总结：上下文工程的核心不是容量管理，而是故障域设计。

## 第一段 [骨]：上下文不是历史，它是下一步行动的状态

07-20 的 ReAct 闭环可以写成：

```text
thought_t -> action_t -> observation_t
     ^                         |
     +------ context_t+1 <-----+
```

危险之处在最后一条箭头：工具输出、网页正文、报错堆栈、模型猜测和用户目标，常被拼成同一种“文本”，一起进入下一轮。模型看见它们，却未必知道：

- 哪些是事实，哪些只是上一轮的假设；
- 哪些已失效，哪些仍是约束；
- 哪些是工具返回，哪些是网页中的指令性文字；
- 哪些任务已经完成，哪些仍未闭环。

于是，错误不只表现为某一步答错。它可能被写回上下文，获得一种“既然前文这么说，后文就继续沿用”的惯性。

这里先立一个核心区分：

```text
transcript: 发生过什么的流水账
state:      为正确完成下一步，当前必须知道什么
```

把完整 transcript 当作 state，是许多 Agent 在长任务中变笨的根源。完整不等于有效；重复出现也不等于更真。上下文越长，过期假设和关键约束反而越容易拥有相似的视觉权重。

### 结构标注

这是今天的总论点：**context engineering 的对象不是“token 数量”，而是下一步决策所依赖的状态表示。** 四种手段都在重写 transcript 到 state 的转换方式。

### 碰撞

如果一个工具第一次返回“文件不存在”，Agent 随后已经创建了文件，但旧报错仍在历史里，那么“文件不存在”究竟是事实，还是一条带时间戳的历史观察？

一个没有时间性与来源标签的上下文，会把二者压成同样的文本。Agent 的错误有时不是推理能力不足，而是**状态表示没有表达‘这个事实已经过期’**。

## 第二段 [骨]：Compaction 不是摘要，而是一次有损状态迁移

**Compaction（上下文压缩）**：当历史接近长度、成本或注意力预算时，把多轮交互重写为更短的状态表示，再以它继续任务。

最幼稚的做法是“请总结以上内容”。它经常生成一段流畅叙述，却删掉真正决定任务成败的低频细节：文件路径、失败命令、用户否决项、尚未验证的假设、精确错误码。

因此，好的 compaction 不应该问“这段对话大意是什么”，而应分槽保留：

```text
Goal
- 当前验收条件是什么

Constraints
- 禁止做什么
- 范围、格式、安全边界是什么

Established facts
- 已由什么来源验证
- 验证时间是什么

Decisions
- 选择了什么
- 为什么排除其他方案

Artifacts
- 文件、URL、任务 ID、哈希、版本

Open loops
- 哪些步骤尚未完成
- 下一动作和阻塞条件是什么

Uncertain / stale
- 哪些只是猜测
- 哪些观察可能已经过期
```

这不是文风差异，而是故障模型差异。普通摘要优化“读起来像原文”；状态压缩优化“恢复任务后还能正确行动”。

### 它切断哪种误差？

长任务中，噪声常近似随轮数累积：每次工具调用都带回大量只用一次的信息。Compaction 定期把历史折叠成结构化状态，使下一轮不必反复注意旧回显。

```text
无压缩:
useful signal + noise_1 + noise_2 + ... + noise_n

有压缩:
verified state + open loops + evidence pointers
```

但 compaction 不是免费午餐。它把“模型还能回看原始细节”变成“模型相信压缩器没有漏掉细节”。因此它引入一个新误差源：**summary drift（摘要漂移）**。

### 最强反驳

> 压缩器也是 LLM；如果它会漏信息，为什么让它重写历史会更可靠？

这个反驳成立。正确回应不是“使用更强模型”，而是降低压缩行为的自由度：

1. 使用固定 schema，而非自由散文；
2. 关键标识符原样复制，不改写；
3. 把证据指针与结论同时保留；
4. 标注“已验证 / 推测 / 过期风险”；
5. 原始记录仍在窗口外可回查，而不是物理删除；
6. 压缩后运行恢复性检查：仅凭 compact state，能否说出目标、约束和下一步？

### 结构标注

Compaction 主要拦截**纵向的噪声累积**，代价是把漏项风险集中到一次有损编码中。

## 第三段 [骨]：子代理隔离不是并发技巧，而是控制污染半径

**Sub-agent isolation（子代理隔离）**：把搜索、调研、编码或验证委派给拥有独立上下文的执行单元；主代理只给最小任务包，并只接收约定格式的结果。

很多人把子代理理解成“多找几个人并行干活”。更深的一层是：它在系统里划出**故障域（failure domain）**。

假设主任务是评估三种技术路线。若所有搜索片段、失败实验和未经证实的推断都进入主窗口，那么其中一条路线的脏上下文会污染其余判断。隔离后：

```text
主代理: 目标、全局约束、比较标准
   |
   +-- 子代理 A: 只研究路线 A
   |      `-> 结论 + 证据 + 不确定项
   |
   +-- 子代理 B: 只研究路线 B
   |      `-> 结论 + 证据 + 不确定项
   |
   `-- 子代理 C: 只做反证与验证
          `-> 通过项 + 失败项 + 复现条件
```

路线 A 里一个网页的提示注入、错误假设或海量无关正文，默认不会进入 B、C 或主代理的推理环境。污染被限制在局部。

### 真正关键的是 handoff

隔离并不会自动提高质量。它把问题从“上下文污染”迁移成“交接失真”。如果主代理只收到一句“研究完成，方案 A 最好”，那么它看不到证据，也无法判断子代理是否越界。

一个可审计的交付包至少应包含：

```text
claim:       结论是什么
status:      verified / inferred / blocked
basis:       证据或真实执行结果
scope:       结论在哪些条件下成立
counterevidence: 有什么反例
artifacts:   文件、URL、日志位置
next_action: 仍需谁做什么
```

这与软件工程里的 API 边界同构：模块内部可以复杂，但跨边界的数据结构必须明确。自然语言“说一下结果”相当于没有类型的接口。

### 最强反驳

> 子代理不知道主上下文，会不会因为缺背景而做出局部正确、全局错误的决定？

会。因此隔离原则不是“背景越少越好”，而是**最小充分上下文（minimum sufficient context）**：给它完成局部任务必需的目标、约束和验收标准，但不给与局部任务无关的历史噪声。

```text
最小权限: 只给完成动作所需的工具能力
最小上下文: 只给正确判断所需的信息范围
```

二者是同一个安全思想。

### 结构标注

子代理隔离主要拦截**横向的污染扩散**，代价是增加委派、交接与全局一致性检查的成本。

## 第四段 [骨]：按需检索，把“记住一切”改成“知道去哪取”

**On-demand retrieval（按需检索）**：长文档、历史日志、代码库和知识库默认停留在窗口之外；Agent 先看索引、目录或元数据，在当前决策确实需要时才取回局部内容。

这不是传统意义上只为“补知识”的 RAG。它还承担上下文的**准入控制**：

```text
eager loading:
任务开始 -> 把所有可能有用的材料塞入上下文 -> 再判断用什么

lazy loading:
任务开始 -> 先识别当前信息缺口 -> 检索最小片段 -> 使用后退出工作集
```

关键变化是：**拥有信息，不等于让信息常驻注意力。**

一个代码 Agent 不必把整个仓库塞进窗口；它需要的是目录地图、符号索引、搜索和局部读取能力。一个研究 Agent 不必永久携带 30 篇论文全文；它需要保留论点到来源的指针，并在要核查时重读原段。

### 它切断哪种误差？

按需检索主要解决“窗口争抢”：大量可能相关但当前无关的文本，会稀释真正约束下一步行动的少量信号。先暴露索引，再逐步展开，可缩小每次推理面对的候选范围。

```text
Level 0: 知道有哪些材料
Level 1: 知道哪份材料可能相关
Level 2: 读取相关章节
Level 3: 只把支持当前 claim 的片段带入工作集
```

这种模式也降低提示注入暴露面：未被取回的外部文本没有机会影响当前决策。但一旦检索回来，来源边界仍要保留；“按需”不等于“可信”。

### 新风险：检索盲区

如果 Agent 不知道自己缺什么，它就不会发起检索；如果索引描述得不好，关键材料会永远留在窗口外。按需检索把风险从“信息太多”转移为“取回策略漏召回”。

因此至少需要两种触发器：

1. **需求触发**：当前决策出现未知变量、外部事实或证据缺口；
2. **验证触发**：即使模型自认为知道，只要结论是时效性事实、高风险动作或验收条件，也必须回源核查。

### 结构标注

按需检索主要拦截**无关材料的注意力竞争**，代价是 Agent 必须学会识别信息缺口，并承担检索漏召回。

## 第五段 [骨]：外部记忆不是更大的 prompt，而是状态的持久层

**External memory（外部记忆）**：把需要跨轮、跨任务或跨上下文窗口保留的状态，写入数据库、文件、向量库、任务系统或结构化笔记，并在需要时读回。

它与按需检索常被混在一起。区分方法是：

```text
按需检索:  已有材料什么时候进入工作集
外部记忆:  当前任务产生的状态如何跨时间保存
```

最有用的类比不是“第二大脑”，而是计算机的内存层次：

```text
当前上下文       = working memory，快、贵、易失
compact state    = checkpoint，供任务恢复
外部记忆         = durable storage，慢、需寻址、可跨会话
原始日志         = audit trail，可追溯但不宜直接全量加载
```

真正困难的不是“存到哪里”，而是三个策略：

### 1. 写什么

如果什么都写，记忆库会变成第二个更脏的 transcript。优先保存：

- 用户明确、稳定的偏好；
- 已验证事实及其来源与时间；
- 不可逆决策及理由；
- 任务 checkpoint 与未决事项；
- 可复用的失败模式与修复方法。

不要把一次性猜测、敏感数据或未经验证的模型推断默认为长期记忆。

### 2. 什么时候更新或失效

“用户使用 Python”与“当前项目必须使用 Python 3.12”有不同的作用域和半衰期。记忆应至少带：

```text
source
created_at
scope
confidence / verification status
expires_at or review condition
supersedes / contradicted_by
```

否则，外部记忆会把过期状态永久化，使错误从一次会话扩散到未来所有会话。

### 3. 如何读回

不能只按语义相似度取 top-k。长期记忆还应按作用域、时间、新旧覆盖关系和权限过滤。相似但过期的记忆，比完全没检索到更危险，因为它带着“系统记得”的权威感。

### 最强反驳

> 既然外部记忆也要检索，那它与 RAG 有什么本质不同？

机制上可能共享检索组件；系统角色不同。RAG 常取回外部知识来回答问题，memory 取回的是 Agent 自身跨时间维持任务连续性所需的状态。前者问“世界资料里有什么”，后者问“我们已经决定、验证或承诺过什么”。二者的写权限、隐私要求、失效规则也不同。

### 结构标注

外部记忆主要拦截**超窗后的状态丢失**，代价是陈旧信息可能被持久化，并在未来反复污染决策。

## 第六段 [肌]：四招不是能力清单，而是一条分层控制链

把四种手段放进同一个 Agent，可以形成下面的边界：

```text
用户目标 + 当前 checkpoint
          |
          v
       主代理上下文
          |
          +-- 不确定、缺证据? ----> 按需检索
          |                           |
          |                         最小片段
          |                           |
          +<--------------------------+
          |
          +-- 可分解的局部探索? ---> 子代理隔离
          |                           |
          |                       结构化 handoff
          |                           |
          +<--------------------------+
          |
          +-- 历史变长? ----------> compaction
          |                           |
          |                       新 checkpoint
          |                           |
          +<--------------------------+
          |
          +-- 需要跨会话保留? ----> 外部记忆
                                      |
                                 带来源与失效规则
```

对应关系可以压成一张表：

| 手段 | 主要拦截对象 | 发生位置 | 新引入的风险 | 验证方式 |
|---|---|---|---|---|
| Compaction | 噪声纵向累积 | 历史 -> checkpoint | 摘要漂移、漏约束 | 恢复性检查、原文指针 |
| 子代理隔离 | 错误横向扩散 | 主上下文 <-> 局部上下文 | handoff 失真、局部最优 | 结构化交付、独立验证 |
| 按需检索 | 无关材料争抢注意力 | 窗口外 -> 工作集 | 漏召回、不知自己不知 | 需求触发 + 强制回源 |
| 外部记忆 | 跨窗状态丢失 | 工作记忆 -> 持久层 | 过期错误永久化 | 来源、时间、覆盖与失效规则 |

以上这一段支撑总论点：四招没有谁能替代谁，因为它们控制的是信息生命周期的不同环节。

## 第七段 [骨]：真正的设计单位是“错误能传播多远”

到这里，可以把 context engineering 重新定义为：

> **Context engineering is the design of information boundaries, lifetimes, and recovery paths for an agent.**
>
> **上下文工程，是为 Agent 设计信息的边界、寿命与恢复路径。**

这个定义比“如何写好 prompt”更接近长程 Agent 的真实难题。

一个强模型若拥有无边界、无时间性、无来源标签的上下文，仍会稳定地沿错误前提走很远；一个稍弱模型若每一步都有局部验证、状态 checkpoint 和污染隔离，反而可能更可靠。

### 旁逸：它与分布式系统的故障隔离是同一个形状

分布式系统不假设机器永不失败，而是设计：超时、重试、幂等、隔离舱、检查点和恢复。上下文工程也不应假设模型永不误读，而应设计：

```text
compaction   <-> checkpoint / log compaction
子代理隔离   <-> bulkhead / failure domain
按需检索     <-> lazy loading / cache miss
外部记忆     <-> durable state / database
```

这组类比的杀伤力在于：**可靠性不来自某个组件绝不犯错，而来自错误发生后不被无限放大，并且系统能恢复。**

### 一个实用验收法

评估上下文设计时，不要只测最终答案正确率。故意注入四类故障：

1. 在历史里放一条已过期的错误假设；
2. 让一个子任务接触恶意或错误材料；
3. 把关键证据藏在默认未加载的长文档里；
4. 在外部记忆里放一条后来被新事实覆盖的旧记录。

然后观察：

- 错误是否越过边界？
- 系统能否定位它来自哪一层？
- 有无恢复路径？
- 恢复是否依赖人工重启整个任务？

这比“上下文窗口支持 1M tokens”更能说明系统是否可用。

### 结构标注

这是全文的最终骨架：**上下文窗口大小是容量指标；错误传播半径与恢复能力才是可靠性指标。**

## 今日最该带走的四个判断

1. **Compaction 是有损状态迁移，不是文摘。** 要保留目标、约束、证据、决策和未决事项，并让原始记录可回查。
2. **子代理的首要价值不只是并行，而是限制污染半径。** 隔离是否有效，取决于最小充分上下文与可审计 handoff。
3. **按需检索让系统拥有“取回能力”，而非让一切常驻窗口。** 它以漏召回风险换取更干净的工作集。
4. **外部记忆解决的是状态持久性，不是 token 不够。** 没有来源、时间与失效规则的记忆，会把临时错误升级成长期偏见。

## 你的压力测试

假设一个代码 Agent 做了 40 轮修改：

- 第 8 轮决定“不升级依赖”，但第 26 轮用户明确允许升级；
- 一个子代理在旧分支上跑测试，报告失败；
- 正确的 API 迁移说明藏在一份尚未读取的文档里；
- 外部记忆仍保存着“该项目禁止升级依赖”。

现在主代理准备根据“测试失败 + 禁止升级”回滚代码。

**四种手段里，哪一种本应最早拦住这个错误？**

不要急着回答“都用上”。先定位每条信息的病：旧约束需要版本与覆盖关系，旧分支测试需要作用域标注，迁移说明需要验证触发，回滚前则需要重新构造当前 checkpoint。真正的问题是：**谁负责判断一条信息已经过期？**

## 读后一句话（不可跳过）

**读完之后，你最想对“上下文越长，Agent 越强”这句话补上的一句限制条件是什么？**

这句话不要求复述四种手段；最好指出你认为最容易被工程团队忽略的一种失败。

## 终局问题

当 compaction、记忆写入、检索 query 和子代理 handoff 都由同一个基础模型生成时，它们可能共享同一种盲点。**除了增加更多 LLM 自评，一个 Agent 系统可以引入什么异质信号，让错误不会在所有上下文边界上被一致地放行？**

## 术语表

| 英文 | 中文 | 本文含义 | 出现位置 |
|---|---|---|---|
| context state | 上下文状态 | 为正确执行下一步而必须保留的信息，而非完整流水账 | 第一段 |
| compaction | 上下文压缩 | 把长历史有损迁移为结构化 checkpoint | 第二段 |
| summary drift | 摘要漂移 | 压缩过程中约束、证据或未决事项被扭曲或遗漏 | 第二段 |
| sub-agent isolation | 子代理隔离 | 用独立上下文限制局部错误的传播范围 | 第三段 |
| handoff | 任务交接 | 子代理向主代理提交可审计结果的接口 | 第三段 |
| minimum sufficient context | 最小充分上下文 | 足以正确完成局部任务、但不携带无关历史的信息集合 | 第三段 |
| on-demand retrieval | 按需检索 | 只在当前决策需要时把窗口外材料取入工作集 | 第四段 |
| external memory | 外部记忆 | 在窗口之外持久保存跨轮、跨任务状态 | 第五段 |
| failure domain | 故障域 | 某个错误默认能够影响到的系统范围 | 第三、七段 |
| checkpoint | 检查点 | 可恢复目标、约束、进度与未决事项的结构化状态 | 第二、六段 |

## 下一步线索

下一步最值得具体拆的是 **compaction 的状态 schema 与恢复性测试**：选一段真实的长 Agent 轨迹，同时产出“普通摘要”和“结构化 checkpoint”，然后隐藏原对话，让另一个执行者仅凭两种压缩结果继续任务。比较的不是摘要是否流畅，而是：约束保留率、未决事项恢复率、错误假设识别率，以及能否从证据指针回到原文。
