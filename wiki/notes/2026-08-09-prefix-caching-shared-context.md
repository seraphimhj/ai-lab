# 伴读：同一段系统提示词，为什么还要算一千遍？——Prefix Caching 与共享上下文的复用边界

> 本次命中：**retrieval 以外·推理系统薄弱点 + Agent / 上下文工程主线 + 端到端闭环**。今天把 07-14 的“单请求 KV cache”推进到“跨请求复用”：上下文写得越长，不只改变模型行为，也在直接改写 serving 的算力账与调度方式。

## 全局地图

### 一句话摘要

Prefix caching 把多个请求完全相同的 token 前缀所产生的 KV 状态只计算一次、跨请求复用；它省掉的是 prefill 计算而非 decode 计算，成立条件不是“文本意思相近”，而是模型、token、位置及相关执行条件都兼容。

### 结构地图

```text
长上下文请求的两段成本

输入 token --------------------------> 首个输出 token -> 后续输出
              prefill                      decode
              高并行计算                   逐 token 串行
                    |                            |
                    |                            `-- 单请求 KV cache 避免重算历史
                    |
                    `-- prefix cache 跨请求复用相同前缀

共享系统提示 / 工具定义 / 文档
              |
              v
       按 token block 建索引
              |
       +------+------+
       |             |
    cache hit      cache miss
       |             |
复用已有 KV      计算新 KV 并入缓存
       |             |
       +------> 继续 prefill 私有后缀 -> decode

真正边界：
相似语义 != 相同 KV；命中率 != 用户体验；缓存优化 != 免费优化
```

## 逐段伴读

## 1. [骨] 先把三个容易混在一起的概念拆开

一次 LLM 请求通常有两个阶段。

**Prefill（预填充）**：模型并行读取全部输入 token，计算每层 attention 所需的 key/value，并产生第一个输出 token 前的内部状态。输入越长，工作越多。

**Decode（解码）**：模型一次生成一个新 token。每一步都依赖上一步，因此串行性强；它通常更受内存带宽和调度影响。

然后才是两种不同层级的 cache：

1. **In-request KV cache（请求内 KV 缓存）**：同一个请求生成下一个 token 时，不再重算此前 token 的 key/value。
2. **Cross-request prefix cache（跨请求前缀缓存）**：另一个请求若以完全相同的 token 序列开头，可直接继承这段前缀的 KV，不再为它做 prefill。

```text
请求 A: [共享前缀 P][用户问题 A][输出 A1 A2 ...]
              |
              +-- 请求内 KV cache 服务 A 的逐步 decode

请求 B: [共享前缀 P][用户问题 B][输出 B1 B2 ...]
              |
              +-- prefix cache 让 B 继承 A 已算过的 P
```

关键区别是：**请求内 KV cache 解决“别在生成每个 token 时重读自己的历史”；prefix cache 解决“别让不同请求重复读共同的历史”。**

**结构标注：核心定义。** 如果不先分阶段，就会把所有“用了 cache”都误解成同一种加速。

### 碰撞

设一个请求输入 20K token，输出 50 token。Prefix cache 命中了前 18K token。你预计它主要改善哪个指标？

不是稳定地把所有阶段都加速 90%，而是主要减少：

- 首 token 前的 prefill 工作；
- 对应的 time to first token（TTFT）；
- prefill 占用的 GPU 计算预算。

它没有消灭后续 50 次自回归 decode，也没有缩小这些输出步骤仍需读取的 KV 状态。

## 2. [肌] 算一笔共享 Agent 上下文的账

假设一个企业 Agent 的每次请求都包含：

```text
系统规则                  3K tokens
工具 schema               5K tokens
固定领域手册             10K tokens
会话历史与当前问题        2K tokens
----------------------------------
总输入                    20K tokens
```

一百个请求若共享前 18K token，却都独立 prefill，系统实际处理的输入量约为：

```text
100 * 20K = 2,000K input tokens
```

若共享前缀已经缓存，忽略块边界和首次填充，后续请求新增的 prefill 量接近：

```text
首次请求: 20K
后续 99 个请求: 99 * 2K
合计: 218K input tokens
```

这是理想化上界，不是延迟保证。真实系统还会受到 cache 容量、驱逐、并发排队、块粒度、模型并行和 decode 竞争影响。但它揭示了一个重要转折：**长系统提示词不必在每次请求中都支付完整计算费，只要请求真的共享同一个前缀。**

**结构标注：数量级证据。** 这一段支持“跨请求复用可以重写 prefill 账本”。

以上 1 段在支持第一节的论证。

## 3. [骨] 为什么“语义一样”仍然不能直接复用？

Attention 中某个 token 的 key/value，不只取决于这个 token 本身，还取决于它此前的整个因果前缀。

可以把第 i 个位置的状态粗略写成：

```text
KV_i = F(model, tokens_1...i, positions_1...i, execution_config)
```

因此，下面两句话在人看来意思接近，缓存看来却完全不同：

```text
A: You must answer concisely.
B: Keep your answers brief.
```

token 序列不同，产生的隐藏状态和 KV 也不同。Prefix cache 不是 embedding 检索，不会因为 cosine 相似就拿 B 的状态冒充 A。那会改变模型计算本身，不再是精确复用。

更隐蔽的是，在共享前缀中间插入一个动态字段，会让插入点之后全部失去复用：

```text
差的排布：
[固定系统提示][user_id][固定工具 schema][固定手册][问题]
                 ^
                 `-- 从这里开始，各用户前缀分叉

更利于复用的排布：
[固定系统提示][固定工具 schema][固定手册][user_id][问题]
                                         ^
                                         `-- 尽量晚分叉
```

但这不是说动态字段永远都应后移。若安全规则要求身份信息在某些内容之前生效，语义和安全约束高于缓存命中。系统优化不能擅自重排会改变模型行为的 prompt。

除了 token 完全一致，工程上通常还需要兼容：

- 同一模型及权重版本；
- 同一 tokenizer 与 chat template；
- 兼容的位置编码与起始位置；
- 兼容的 adapter / LoRA 等运行配置；
- 不被安全隔离策略禁止共享。

**结构标注：核心边界。** Prefix cache 是对同一计算子图的复用，不是对“意思差不多”的近似替换。

### 注疏：它和编译器的公共子表达式消除是同一个形状

编译器看到两处完全相同的表达式，可以算一次、复用结果；只要输入或执行语义变了，就不能因为“结果大概相近”而复用。

```text
公共子表达式消除: 相同输入 -> 相同中间结果 -> 复用
Prefix caching:    相同前缀 -> 相同 KV 状态   -> 复用
```

这里的关键词不是 cache，而是 **referential stability（引用稳定性）**：复用成立，是因为同一输入在相同条件下产生可复用的中间状态。

## 4. [肌] 系统如何找到“你和谁共享了多长的前缀”？

实现不一定把整段前缀做成一个巨大的 cache item。常见方式是把 token 切成固定大小的 block，并让每个 block 的标识依赖前一块：

```text
block_1_hash = H(model_config, tokens_1)
block_2_hash = H(block_1_hash, tokens_2)
block_3_hash = H(block_2_hash, tokens_3)
```

这种链式标识很重要。第三块即使 token 内容碰巧一样，只要此前路径不同，也不能被错认成相同状态。

另一种直观视角是 radix tree / prefix tree（基数树 / 前缀树）：

```text
ROOT
  |
  +-- shared system prompt
        |
        +-- tool schemas
              |
              +-- handbook v1
              |     |
              |     +-- user A suffix
              |     `-- user B suffix
              |
              `-- handbook v2
                    `-- user C suffix
```

调度器沿 token 路径寻找最长可复用前缀。分叉之前共享，分叉以后分别计算。缓存空间不足时，还必须决定驱逐谁：最近最少使用、代价最高的长前缀、还是即将被一批请求重复使用的前缀？

这说明 prefix cache 不只是一张哈希表问题，它和调度绑定：**算好的 KV 留在哪里、下一个请求送到哪张 GPU、同一前缀请求是否尽量汇聚，都会改变实际命中率。**

**结构标注：机制展开。** Block hashing 解决正确识别，prefix-aware routing 解决让可复用状态和请求真正相遇。

以上 1 段在支持第三节“精确前缀复用”的论证。

## 5. [骨] 上下文工程不再只是“让模型读懂”，也在决定系统账单

过去谈 prompt，常问：这些说明能否让模型遵循任务？Prefix caching 迫使我们再问三个系统问题：

1. 哪些内容在请求之间稳定？
2. 第一个动态 token 出现在哪里？
3. 稳定内容的版本会多频繁变化？

把共享内容放在前面、动态内容放在后面，通常提高可复用长度：

```text
stable -> stable -> stable -> dynamic -> dynamic
          可共享区             私有区
```

但“把静态内容都塞前面”还不够。若工具 schema 每次只因字段顺序、空格或时间戳变化，token 就会变化，cache 被无意义地击穿。因此需要 canonicalization（规范化）：

- 工具按稳定顺序序列化；
- 避免在共享区注入每次变化的时间戳、request ID；
- 固定 chat template 与空白格式；
- 给知识手册明确版本，而不是每次重排全文；
- 将真正个性化的记忆放在共享前缀之后。

这里有一个反直觉点：**RAG 检索出的文档即使频繁重复，也未必自然形成 prefix hit。** 如果每个请求的文档集合和排序不同，第一处分叉会很早。要提高复用，可能需要稳定的公共知识前缀、cache-aware document ordering，或显式的共享会话树；但排序首先仍应服务于答案质量，不能为了缓存把最相关证据藏到不利位置。

**结构标注：上下文工程结论。** Prompt 的稳定性、顺序和版本化已成为 serving 接口的一部分。

### 压力测试

如果团队把命中率设成唯一 KPI，工程师可能会做什么？

- 固定更多上下文，即使其中多数无关；
- 为了共享而减少个性化信息；
- 延迟更新系统规则和知识版本；
- 把请求路由到有 cache 的 GPU，即使那里队列更长。

于是 cache hit rate 上升，端到端任务质量或延迟却可能变差。这正是 Goodhart 定律在推理系统里的一个实例：代理指标一旦成为目标，就可能偏离真正目标。

## 6. [骨] 三处陷阱：命中了，也不等于赚到了

### 6.1 命中收益与排队成本会打架

假设 GPU A 已有目标前缀，但队列很长；GPU B 没有 cache，却立即可做 prefill。最优选择取决于：

```text
去 A 的等待时间
vs
去 B 重新 prefill 的时间与资源成本
```

Prefix-aware routing 若只追逐命中，会制造热点。成熟调度器要把缓存亲和性与负载一起优化。

### 6.2 大前缀可能污染 cache

一个只用一次的超长文档会占据大量 KV 空间，驱逐真正高频的系统前缀。此时“缓存了更多 token”反而降低未来收益。驱逐策略应估计复用概率和重算成本，而不是只看长度。

### 6.3 跨租户共享有安全边界

即使系统只复用内部 KV、不直接返回原文，跨租户共享也需考虑：

- timing side channel（计时侧信道）：命中造成的延迟差可能暴露某前缀是否存在；
- cache key 是否包含租户、adapter、权限和模型版本；
- 私有上下文是否允许进入共享池；
- 缓存清理是否遵守数据保留策略。

因此物理上可复用，不等于治理上允许复用。最保守做法是租户隔离；更激进的共享必须建立在明确的威胁模型和访问控制上。

**结构标注：最强限定。** Prefix cache 的正确性只回答“能不能复用这段计算”，调度、安全与经济性才回答“应不应该复用”。

## 7. [骨] 端到端闭环：缓存会反过来塑造上下文

把整条链接起来：

```text
Prompt 结构与版本策略
        |
        v
共享前缀长度与更新频率
        |
        v
cache 命中、KV 占用、GPU 路由
        |
        v
TTFT、吞吐与 serving 成本
        |
        v
团队优化 KPI 和模板设计
        |
        `----------------------> 反过来改 Prompt
```

这与前几天“评测协议塑造模型”是同一类闭环：系统测什么、奖励什么，最终会改变上游产物。若只奖励 token cache hit，上下文会越来越静态；若只奖励回答质量，系统可能忽视大量可避免的重复计算。

真正应优化的是约束下的总目标，例如：

```text
最小化：端到端延迟 + GPU 成本
约束：答案质量、安全隔离、知识新鲜度不低于阈值
```

因此 prefix caching 最值得学的，不是“又一个推理加速技巧”，而是一条架构原则：**共享计算必须被上下文结构显式暴露，才能被系统可靠复用；而任何复用策略都会反过来影响内容组织。**

**结构标注：闭环结论。** 上下文工程、推理系统和组织 KPI 不是三件事，而是同一控制回路的三个位置。
