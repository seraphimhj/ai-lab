# 伴读：Self-RAG / CRAG——检索不再是一条管道，而是一个可纠错的动作

> 本次命中：**RAG / 检索主线 + Agent / 上下文工程主线**；补的是从“怎么检索”到“何时检索、检索错了怎么办”的断层。

材料：
- Asai et al., *Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection*（arXiv:2310.11511）
- Yan et al., *Corrective Retrieval Augmented Generation*（arXiv:2401.15884）

## 全局地图

### 一句话摘要

传统 RAG 把检索结果当成既定事实塞进上下文；Self-RAG 和 CRAG 则把“是否需要检索、证据是否相关、答案是否被证据支持”变成显式判断，从而让错误在进入生成器前后都有机会被拦截。

### 结构地图

```text
传统 RAG
query -> 固定检索 top-k -> 全部拼进 prompt -> 生成
              |
              +-- 错文档也会成为有权威外观的噪声

Self-RAG
当前生成状态 -> 要检索吗? -> 检索 -> 相关吗? -> 生成一个片段
       ^                                  |
       +------ 有支持吗? 有用吗? <--------+

CRAG
query -> 初次检索 -> 外置 evaluator
                       |
          +------------+------------+
          |            |            |
       Correct      Ambiguous     Incorrect
          |            |            |
       精炼文档      双路并用       丢弃并查 Web
          +------------+------------+
                       |
                     生成
```

关键差别不只是“多了一个评分器”，而是**控制流变了**：检索从一次性的预处理，变成可以跳过、重做、降权和验证的动作。

### 段落分类概览（Agent 判断）

- [骨] 病灶：检索命中不等于证据可用，静态 RAG 缺少质量控制。
- [骨] Self-RAG：把检索与自我批评写进生成序列。
- [肌] reflection tokens：把“需要、相关、支持、有用”拆成不同判断。
- [骨] CRAG：用外置评估器把检索结果分成 Correct / Ambiguous / Incorrect，并触发不同动作。
- [骨] 二者关系：Self-RAG 偏向生成过程内的自反控制，CRAG 偏向生成前的检索纠错；可以组合，但不能把它们当成同一方法。
- [肌] 工程落地：先做可观测的检索门控，再谈端到端训练。

## 第一段 [骨]：真正的病不是“没检索”，而是“错检索仍被信任”

### 原文锚点

> “However, indiscriminately retrieving and incorporating a fixed number of retrieved passages, regardless of whether retrieval is necessary, or passages are relevant, diminishes LM versatility or can lead to unhelpful response generation.”
>
> “然而，不管检索是否必要、段落是否相关，都不加区分地检索并纳入固定数量的段落，会削弱语言模型的灵活性，也可能导致无益的回答。”

### 直译层（信）

作者反对的不是检索，而是 **indiscriminately（不加区分地）** 检索：每个问题固定取 top-k，再把它们全部放入上下文。这样做暗含两个未经检验的前提：

1. 这个问题需要外部知识；
2. 相似度最高的文档足以支持答案。

### 意译层（达）

传统 RAG 常把 retriever 当“事实供应器”，但 retriever 实际只是在回答：“哪些文本在表示空间里最像这个 query？”它没有承诺：

- 文档真的回答了问题；
- 文档中的关键句是正确的；
- 文档足以支持模型即将写出的那句话；
- 此时调用检索比直接回答更好。

因此，RAG 可能把模型原本的“不知道”，升级成“拿着错误证据自信地说”。**检索错误并不是普通噪声；一旦进入上下文，它会获得证据的外观。**

### 结构标注

这是全文的核心病灶：**召回是候选生成，不是事实认证。**

### 碰撞

回看你之前学过的 SPLADE、ColBERT、MUVERA：它们主要优化的是“把更可能相关的候选排到前面”。但即使 Recall@k 提高，也没有回答另一个问题：**top-k 里的内容是否足以支持当前要生成的 claim？**

这两个指标不要混：

```text
retrieval relevance: 文档和问题相关吗?
claim support:       文档能推出这句回答吗?
```

一篇介绍乔布斯的文章与“乔布斯哪年出生”高度相关；如果截取段落里没有出生年份，它对该 claim 仍然是“相关但不支持”。

## 第二段 [骨]：Self-RAG 把 RAG 改写成逐步决策

### 原文锚点

> “SELF-RAG retrieves on demand and generates outputs through an iterative process of generating reflection tokens and task outputs.”
>
> “Self-RAG 按需检索，并通过反思标记与任务输出交替生成的迭代过程产生答案。”

### 直译层（信）

**reflection token（反思标记）**：模型生成序列中的特殊控制标记，用来显式表达对检索需求、文档相关性、证据支持度或回答效用的判断。它不是模型写给用户看的自然语言反思，而是参与控制检索和解码的离散信号。

### 意译层（达）

普通 RAG 的控制流在生成前就结束了：检索一次，然后一路写到底。Self-RAG 则让模型在生成过程中反复做四种不同判断：

1. **Retrieve**：此刻需要检索吗？
2. **ISREL**：取回的段落与问题相关吗？
3. **ISSUP**：当前生成内容被该段落支持到什么程度？
4. **ISUSE**：这段回答对任务有多大效用？

可以把它看成给生成器加了几个“内部仪表盘”：

```text
生成状态
  |
  +-- [Retrieve=No]  ----> 直接继续
  |
  +-- [Retrieve=Yes] ----> 取回文档
                              |
                         [ISREL]
                              |
                         生成内容片段
                              |
                    [ISSUP] + [ISUSE]
                              |
                     继续 / 换证据 / 降权
```

关键不是模型会说“我反思了”，而是这些标记能在训练和解码时产生约束：候选答案若证据支持弱，即使语言上很流畅，也可以被降低分数。

### 点睛层（雅）

这里的 **self-reflection** 很容易被误译成拟人化的“模型自省”。更准确的理解是：**把原本藏在系统代码里的 if/else，变成模型可预测、可训练的控制变量。**

它与 ReAct 的同构之处是：两者都把“行动”插入 token 序列；差别是 ReAct 的动作通常是调用通用工具，Self-RAG 的动作与评价专门围绕 retrieval / evidence 展开。

### 结构标注

这是 Self-RAG 的核心机制：检索不再只是 prompt 前处理，而成为生成策略的一部分。

### 压力测试

最强反驳是：**判断证据好坏的仍然是模型；如果模型本来就会犯错，多生成几个自评 token 为什么会更可靠？**

答案不是“模型突然有了自知之明”。Self-RAG 训练阶段先借助 critic 为数据标出反思信号，再训练 generator 学这些标记；推理时还可以把多个维度纳入候选排序。它提供的是“额外、可监督的错误接口”，不是可靠性证明。

所以应该记住：

```text
reflection token != truth oracle
reflection token == 可训练、可观测、可用于控制的判断接口
```

如果反思判断与生成错误高度相关，它就可能拦错；如果二者同源共错，它只会把错误说得更有结构。

## 第三段 [肌]：四类判断为什么不能合成一个“confidence”

把所有判断压成一个置信度看似简单，却会丢掉故障位置：

| 判断 | 真正问的事 | 失败时该做什么 |
|---|---|---|
| Retrieve | 当前问题是否需要外部知识 | 跳过检索或触发检索 |
| ISREL | 文档是否与问题相关 | 丢弃、换文档 |
| ISSUP | 文档是否支持生成的具体内容 | 改写 claim、补证据 |
| ISUSE | 回答是否完成用户任务 | 重组答案、补遗漏 |

一个回答可能出现以下组合：

```text
文档相关 = 是
事实支持 = 是
回答有用 = 否
```

例如用户问“怎么修”，模型只给了正确的原理史。事实没有错，但任务没有完成。反过来，一个回答也可能非常有用，却引用了不支持它的材料。

这就是 Self-RAG 对端到端闭环的启发：**不要只报一个总分；用评分维度定位错误发生在哪一环。**

以上这一段在支撑第二段：reflection tokens 的价值，部分来自故障分解，而不只是“多一次自评”。

## 第四段 [骨]：CRAG 把纠错器放在生成器外面

### 原文锚点

> “A lightweight retrieval evaluator is designed to assess the overall quality of retrieved documents for a query, and different knowledge retrieval actions are triggered based on the confidence degree.”
>
> “CRAG 设计了一个轻量检索评估器，判断针对某个查询的检索文档整体质量，并依据置信程度触发不同的知识检索动作。”

### 直译层（信）

**retrieval evaluator（检索评估器）**：位于 retriever 之后、generator 之前的轻量模型，对 query-document 关系评分；系统再根据阈值将当前检索状态分流。

### 意译层（达）

CRAG 不要求生成模型自己承担全部控制。它在初次召回后加一个质检站，并把结果分成三态：

```text
Correct:
  至少有高置信文档
  -> 保留有用知识，并做细粒度知识精炼

Incorrect:
  所有文档都低置信
  -> 丢弃这批结果，转向 Web 搜索等外部来源

Ambiguous:
  评估器无法明确判对或判错
  -> 同时保留精炼后的内部知识与外部补检结果
```

这里最值得学的不是三个英文标签，而是 **abstention（拒绝武断）**：CRAG 没把中间分数硬切成对或错，而是允许“不确定”触发成本更高但更稳妥的双路策略。

此外，CRAG 的“精炼”不只是整篇保留或丢弃。它会把文档拆成更细的知识片段，分别评分、过滤，再重组相关内容。这样能避免一篇整体相关的长文把大量无关段落一起塞进上下文。

### 结构标注

这是 CRAG 的核心：**用外置 evaluator 做检索后验质检，并让评分真正改变后续动作。**

### 碰撞

很多系统已经有 reranker，但 reranker 和 CRAG 的 evaluator 不完全相同：

```text
reranker:  在现有候选中重新排序，“谁更好?”
CRAG:      判断整批候选是否值得信，“这批还能不能用?”
```

如果候选池整体都错，reranker 只能挑出“最不坏”的那个；CRAG 的 Incorrect 分支允许承认候选池失效，换知识源。这是从 ranking 到 control 的一步。

## 第五段 [骨]：Self-RAG 与 CRAG 不是替代关系，而是两处不同的保险丝

最简洁的区分：

| 维度 | Self-RAG | CRAG |
|---|---|---|
| 控制者 | 生成模型预测反思标记 | 外置轻量检索评估器 |
| 主要时点 | 生成过程中，按需、多次 | 初次检索后、生成前 |
| 主要对象 | 是否检索、相关性、claim 支持度、效用 | 整批检索质量与纠错动作 |
| 训练侵入性 | 较高，需要训练反思行为 | 较低，可挂到不同生成器前 |
| 典型风险 | 自评与生成同源共错 | 阈值失准、Web 来源质量不稳 |

组合起来，它们覆盖两个不同故障面：

```text
query
  |
retriever
  |
CRAG evaluator ------ 拦“坏证据进入上下文”
  |
generator
  |
Self-RAG ISSUP ------ 拦“答案越过证据边界”
  |
answer
```

这正好接上 07-20 的 Agent 误差复合：纠错的关键不是在终点笼统问“答案好吗”，而是**在误差跨环传播之前放保险丝**。

### 旁逸：它与类型系统是同一个形状

这里的论证结构与程序语言里的类型系统同构：

- 静态 RAG 像把外部输入直接强制转换成可信类型；
- evaluator 像边界校验；
- reflection token 像把中间状态的类型证明留在计算图里；
- Ambiguous 像 `Option` / `Result`，不允许“不确定”悄悄伪装成确定值。

好系统不是从不出错，而是让“不确定”拥有一种不能被忽略的表示。

### 结构标注

这是两篇材料汇合后的主结论：**Agentic RAG 的本质不是“多调几次搜索”，而是让检索质量影响控制流。**

## 第六段 [肌]：如果今天落地，不要一上来复刻论文训练

可以按四级成熟度递进：

### Level 0：先把检索链变得可观测

每次记录：

- 为什么触发检索；
- query 如何改写；
- top-k 与各阶段分数；
- 最终答案中的 claim 引用了哪个片段；
- 没有证据支持的 claim 有哪些。

没有这些日志，后续 evaluator 只是在黑箱上再叠一层黑箱。

### Level 1：规则或小模型做门控

先解决两个高收益问题：

1. 哪些请求根本不该检索，例如纯改写、格式转换；
2. 哪些检索结果明显不可用，例如实体完全错位、关键字段缺失。

### Level 2：三态路由，不只做二分类

```text
高分 -> 使用 + 精炼
低分 -> 换 query / 换索引 / 换来源
中间 -> 双路检索 + 保守回答 + 显式不确定性
```

阈值不能只按 evaluator 的离线准确率定。应按业务损失定：错答成本高的任务，提高进入 Correct 的门槛；延迟敏感任务，减少 Ambiguous 分支的昂贵补检。

### Level 3：做 claim-level support

把答案拆成可核验 claim，逐条判断证据是否支持。此时系统才从“文档看起来相关”迈到“答案没有越过证据边界”。

以上工程段在支持两篇论文共同的骨架：判断必须连接动作，否则 evaluator 只是 dashboard，不是闭环。

## 今日最该带走的三个判断

1. **高召回率解决候选缺失，不解决证据误用。** Retriever 的分数不是事实置信度。
2. **Self-RAG 把控制与批评内化进生成序列；CRAG 把检索质检外置成可插拔路由器。** 二者拦截的是不同环节。
3. **Agentic RAG 的分水岭是：评价结果会不会改变下一步动作。** 只让模型写一段“自我反思”而控制流不变，不算真正纠错。

## 你的压力测试

假设内部知识库召回了一篇与问题高度相关的旧文档，Web 搜索找到一篇时间更新但来源较弱的新文档：

```text
内部文档: 来源可靠，时间过期
Web 文档:  时间最新，来源可疑
```

CRAG 的 Correct / Ambiguous / Incorrect 三态还不够，因为“相关性”“时效性”“来源可靠性”被压成了一个分数。**你会把 evaluator 拆成哪几个维度？当这些维度冲突时，控制策略由谁决定？**

不要急着回答“加权求和”。一旦加权求和，你可能又制造了昨天刚讨论过的病：平均值把决定性的少数信号抹掉。

**读完之后，你最想对 Self-RAG / CRAG 的作者说的一句话是什么？**

可以赞同，也可以指出它们把哪个真正困难的问题推迟了。

## 终局问题

如果“检索器、评估器、生成器”都来自相似训练分布，它们可能在同一个盲区里一致地判错。**一个闭环系统需要什么样的异质性，才能让 evaluator 真正成为纠错者，而不是 generator 的回声？**

## 术语表

| 英文 | 中文 | 本文含义 | 出现位置 |
|---|---|---|---|
| on-demand retrieval | 按需检索 | 由当前生成状态决定是否检索，而非固定 top-k | 第二段 |
| reflection token | 反思标记 | 对检索需求、相关性、支持度、效用的显式控制标记 | 第二、三段 |
| retrieval evaluator | 检索评估器 | 在召回后判断 query-document 质量并触发路由 | 第四段 |
| knowledge refinement | 知识精炼 | 拆分、评分、过滤并重组文档中的细粒度片段 | 第四段 |
| claim support | 论断支持度 | 证据是否足以推出答案中的具体陈述 | 第一、六段 |
| abstention | 拒绝武断 | 允许系统表达不确定，并进入不同处理路径 | 第四段 |
