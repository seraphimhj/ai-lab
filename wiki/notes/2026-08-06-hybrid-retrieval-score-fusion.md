# 伴读：BM25 的 12 分和 Dense 的 0.82，为什么不能直接相加？

> 本次命中：**RAG / 检索 / Embedding + 统一数学框架 + 端到端闭环**；补的是“异构召回分数如何进入同一个排序决策，以及融合偏差怎样传到生成端”的薄弱点。

材料锚点：Cormack, Clarke & Buettcher, *Reciprocal Rank Fusion Outperforms Condorcet and Individual Rank Learning Methods*（SIGIR 2009），并把 Reciprocal Rank Fusion（RRF）放进今天的 BM25 + dense hybrid retrieval 管线里重读。

## 全局地图

### 一句话摘要

混合检索真正的难题不是“同时跑 BM25 和向量检索”，而是：**两套分数没有共同单位，系统必须先决定相信谁、相信到什么程度；RRF 用名次绕开量纲问题，但也会丢掉分差和置信度。**

### 结构地图

```text
查询 q
  |
  +--> BM25 ----------> lexical score ----> rank_B
  |      字面匹配                             |
  |                                          +-->
  +--> Dense ---------> cosine/dot score --> rank_D
         语义匹配                             |
                                             v
                                      fusion rule
                                   /       |       \
                            score sum   normalized   RRF
                                |          score     rank
                                +-----------+---------+
                                            |
                                            v

                                            v

                                            |
                                            v

```

## 一、[骨] 分数看起来都是数字，却不是同一种量

设同一个文档在两路检索中得到：

```text
BM25 score       = 12.0
Dense similarity = 0.82
```

最危险的反应是：“都是相关性分数，直接相加不就行了？”

问题在于，这两个数字没有共同的零点、单位和尺度。

- **BM25 score（BM25 分数）**：来自查询词频、文档词频、逆文档频率和长度归一化。它随查询长度、语料统计和实现参数变化，不是概率。
- **cosine similarity（余弦相似度）**：比较两个向量夹角；若向量已归一化，通常落在有限区间，但有效分布取决于 embedding 模型和语料。
- **dot product（点积）**：还受向量模长影响，甚至与余弦分数不在同一几何尺度上。

因此：

```text
12.0 + 0.82
```

在算术上合法，在语义上却可能像：

```text
12 摄氏度 + 0.82 米
```

更隐蔽的是，即使把两路分数都压到 0 到 1，也不等于完成了校准。min-max normalization 只把当前候选集的最大值映到 1、最小值映到 0；它没有证明“两路的 0.8 表示相同置信度”。一条异常高分文档还会压扁其余文档的相对差异。

### 结构标注

这是全文的起点：**融合不是排序结果的后处理细节，而是在给不同证据系统分配解释权。**

### 碰撞问题

当你给 hybrid search 写下 `alpha * dense + (1-alpha) * BM25` 时，alpha 真的是“语义与字面的业务权重”，还是在补偿两套分数任意的数值尺度？如果模型版本一换，alpha 的含义还在吗？

## 二、[骨] RRF：不问你考了多少分，只问你排第几

### 原文锚点

论文标题中的核心短语是：

> “Reciprocal Rank Fusion”
>
> “倒数排名融合”

首次出现的术语：

- **Reciprocal Rank Fusion（倒数排名融合，RRF）**：把文档在每个检索器中的名次转成倒数权重，再跨检索器求和。

其基本形式是：

```text
RRF(d) = sum over retrievers i of 1 / (k + rank_i(d))
```

其中：

- `rank_i(d)` 是文档 d 在第 i 路检索中的名次；
- `k` 是平滑常数，控制榜首相对后续名次有多大优势；
- 未进入某一路候选集的文档，可视为该路不贡献分数。

### 直译层（信）

RRF 的动作非常克制：它不尝试把 BM25 的 12.0 翻译成 dense 的 0.82，也不声称估计了“真实相关概率”。它只保留每一路最可靠、最可比较的信息：**顺序**。

### 意译层（达）

可以把两路检索器看成两个使用不同评分标准的评委。一个给百分制，一个给五颗星。直接加原始分会让量纲支配结果；RRF 要求每位评委只交名次表，然后按“第一名比第五名更值得信”来投票。

```text
BM25 榜： A, B, C, ...
Dense榜： C, A, D, ...

A：两边都靠前 -> 得到两份较强支持
C：两边也靠前 -> 得到两份较强支持
B：只在 BM25 靠前 -> 保住字面匹配的少数信号
D：只在 Dense 靠前 -> 保住语义匹配的补充信号
```

这正是 RRF 的鲁棒性来源：它对原始分数的缩放、平移和分布形状不敏感。只要各路内部名次不变，融合结果就不变。

### 点睛层（雅）

这里的 *reciprocal* 不是“互惠”，而是数学上的“倒数”。`rank = 1` 变成 `1/(k+1)`；名次越后，贡献越小。中文只说“排名融合”会漏掉它的衰减机制，因此更准确的是“倒数排名融合”。

### 结构标注

这是方法骨架：RRF 用**放弃分数信息**换取**跨检索器的可比性和稳定性**。

### 注疏：它和集成学习是同一个形状

这里的结构很像 ensemble voting：基模型的 logit 未必校准到同一尺度，于是先聚合更稳健的偏序或投票。它不是证明每个评委都对，而是在减少某一个评委凭数值尺度独占结果的机会。

## 三、[肌] 实体查询最能看出混合检索为何必要

考虑查询：

```text
“ACME-XG42 逆变器故障码 E17”
```

两路检索器可能形成不同榜单：

```text
BM25
1. ACME-XG42 手册：E17 温度传感器异常
2. ACME-XG42 安装指南
3. ACME-XG41 故障码表

Dense
1. 光伏逆变器常见温度故障排查
2. 传感器断路诊断流程
3. ACME-XG42 手册：E17 温度传感器异常
```

BM25 抓住型号与错误码这类低频、高信息 token；dense 抓住“逆变器 - 温度 - 传感器 - 排查”的语义同构。真正的答案文档在两边都靠前，RRF 会把这种**跨系统一致性**当作强信号。

但假如查询改为自然语言：

```text
“设备一热就停机，面板提示传感器异常，怎么排查？”
```

用户没有输入精确型号和错误码，dense 的同义匹配价值会上升；若查询是精确工单号、药品名或 API symbol，BM25 的 exact match 价值通常更高。

这说明最优融合权重可能依赖查询类型：

```text
查询特征
  |
  +--> 专名/编号/代码很多 ----> lexical 倾向更强
  |
  +--> 描述性自然语言 -------> semantic 倾向更强
  |
  +--> 两者兼有 -------------> 保持互补，再交给 reranker
```

以上三段在支持第二节的论证：融合的价值不在“平均两套答案”，而在让两类互补证据都有进入后续判断的机会。

## 四、[骨] RRF 的代价：它不知道“险胜”和“碾压”不同

RRF 只看名次，因此下面两种榜单对它完全一样：

```text
情形 A：第 1 名与第 2 名分数几乎相同
情形 B：第 1 名远高于第 2 名，其余都像噪声
```

只要顺序相同，RRF 看不见分差。这是它主动丢掉的信息。

因此要把三类融合方法的假设分开：

| 方法 | 保留什么 | 依赖什么假设 | 主要风险 |
|---|---|---|---|
| 原始分数加权 | 名次 + 分差 | 各路分数天然可比 | 量纲支配结果 |
| 归一化后加权 | 名次 + 候选集内相对分差 | 归一化后尺度近似可比 | 对候选集和异常值敏感 |
| RRF | 名次 | 各路内部排序有信息 | 丢掉置信间隔 |
| 学习融合 / reranker | 查询、文档及多路特征 | 有代表性的监督数据 | 过拟合与分布漂移 |

### 最强反驳

“既然 cross-encoder reranker 能直接读 query-document 对，为什么不跳过融合？”

因为 reranker 通常只能重排一个有限候选集。它可以纠正“候选文档之间谁更相关”，却不能复活**从未进入候选集**的文档。融合首先承担的是候选覆盖职责：

```text
召回 / 融合：宁可多带几个有希望的候选，控制漏检
reranker：在有限候选里做更昂贵的精排，控制误排
```

若 BM25 top-k 与 dense top-k 在融合前就截得太浅，RRF 再漂亮也只是对两个残缺榜单投票。这里接上昨天的 RAG 故障定位：先测各路和并集的 evidence recall，再评融合后的 nDCG/MRR，最后才看生成答案。

### 压力测试

如果同一个错误知识库被 BM25 和 dense 同时索引，两路“一致赞成”并不代表事实正确。RRF 聚合的是检索器共识，不是世界真相。**相关性共识不能替代来源真实性。**

### 结构标注

这是边界段：RRF 修的是跨分数尺度，不修候选集缺失、语料错误、查询意图误判和生成器不会使用证据。

## 五、[筋] 把融合放回端到端闭环

作者从融合规则过渡到系统设计时，最值得保留的不是某个固定参数，而是一套分层验证：

```text
第一层：单路召回
  - BM25 evidence recall@k
  - Dense evidence recall@k

第二层：候选互补
  - union recall@k
  - 两路命中文档重合率
  - 仅 BM25 / 仅 Dense 找到的关键证据比例

第三层：融合排序
  - fused MRR / nDCG
  - 不同 query slice 下的效果

第四层：精排与生成
  - reranker 是否保住关键证据
  - generator 的有效召回与忠实度

第五层：线上漂移
  - 新实体、新术语、长尾编号是否让 lexical 路权重上升
  - 口语化查询是否让 semantic 路贡献上升
```

这里尤其不要只报告一个总体平均值。至少按以下 query slice 分层：

- 精确实体、型号、错误码；
- 同义改写、口语描述；
- 多约束组合查询；
- 时间敏感或版本敏感查询；
- 需要多跳证据的查询。

否则总体最优的融合规则，可能正在系统性牺牲最重要的长尾实体。
