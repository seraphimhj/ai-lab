# 伴读：RAG 评测不是一个分数，而是一张故障定位图

> 本次命中：**RAG / 检索 / Embedding + 模型评估 + 端到端闭环**；补的是“召回、上下文利用、生成忠实度如何沿链条传导”的薄弱点。

材料锚点：Es et al., *RAGAS: Automated Evaluation of Retrieval Augmented Generation*（EACL 2024），并借用 Liu et al., *Lost in the Middle*（TACL 2023）做一次压力测试。

## 全局地图

### 一句话摘要

一个 RAG 系统答错时，端到端准确率只能告诉你“病了”，不能告诉你病在**证据没取到、证据被噪声埋住、模型没用证据，还是评委判错了**；有效评测必须把结果拆成可干预的条件链。

### 结构地图

```text
问题 q
  |
  v
检索器 ------> 候选上下文 c
  |                |
  |                +--> 覆盖：需要的证据到了吗？
  |                +--> 聚焦：无关内容挤占了多少？
  |                +--> 可用：证据的位置/格式让模型读得到吗？
  |                         |
  v                         v
检索评测                 生成器 ------> 答案 a
                            |             |
                            |             +--> 忠实：说法受 c 支持吗？
                            |             +--> 相关：回答了 q 吗？
                            |             +--> 正确：与事实/金标一致吗？
                            v
                         端到端结果
                            |
                            v
                    评委是否校准、是否有偏？
```

- `[骨]` 端到端分数为什么不可诊断

## 一、[骨] 端到端准确率是体温计，不是 CT

### 原文锚点

> “We have highlighted the need for automated reference-free evaluation of RAG systems.”
>
> “...an evaluation framework that can assess faithfulness (i.e. is the answer grounded in the retrieved context), answer relevance (i.e. does the answer address the question) and context relevance (i.e. is the retrieved context sufficiently focused).”

### 直译层（信）

> “我们强调了对 RAG 系统进行自动化、无参考答案评估的必要性。”
>
> “……一种能够评估忠实度（即答案是否以检索到的上下文为依据）、答案相关性（即答案是否回应了问题）以及上下文相关性（即检索到的上下文是否足够聚焦）的评估框架。”

首次出现的三个术语：

- **faithfulness（忠实度）**：答案中的主张能否由给定上下文推出。
- **answer relevance（答案相关性）**：答案是否正面回应用户问题。
- **context relevance（上下文相关性）**：送入生成器的内容是否聚焦于当前问题，而非塞满无关材料。

### 意译层（达）

论文真正改变的不是“又发明三个指标”，而是**把 RAG 从一个黑盒拆成两个可分别问责的部件**：检索器负责把可用证据送到场，生成器负责依证作答。只盯最终正确率，就像发现包裹没到却只处罚收件人：你不知道它是仓库没出货、物流送错门，还是收件人拿到后没拆。

### 结构标注

这是全文的核心论点：**评测首先是归因问题，其次才是打分问题。**

### 碰撞问题

你看到“答案错了”时，第一反应通常是换 embedding、调 prompt，还是换模型？如果没有先做归因，这三个动作都可能只是碰运气。

## 二、[骨] “有依据”不等于“是真的”

最容易混淆的是下面三句话：

```text
忠实：答案是否忠于给它的材料？
正确：答案是否符合外部事实或金标？
相关：答案是否真的回答了问题？
```

它们不是同义词。设上下文错误地写着“药物 X 的标准剂量是 500mg”，模型原样回答 500mg：

- 忠实度：高，因为答案受到上下文支持；
- 正确性：可能为零，因为源文档本身错了；
- 相关性：仍然高，因为它确实回答了剂量问题。

反过来，模型靠参数记忆给出正确剂量 50mg，却与上下文冲突：

- 正确性：高；
- 忠实度：低；
- 对一个要求“只依据公司知识库回答”的系统而言，这仍是严重失败。

### 点睛层（雅）

中文里“忠实”和“正确”都容易被压成“没胡说”。英文把二者刻意拆开：

- *faithful to the context*：对材料守信；
- *factually correct*：对世界为真。

RAG 的特殊困难正是：**材料与世界之间还隔着一层数据治理。** 评估生成器的忠实度，不能替代评估知识库的真实性与时效性。

### 结构标注

这是概念边界段：它阻止团队把一个漂亮的 faithfulness 分数误当成系统安全。

### 压力测试

如果一个系统忠实度从 0.85 升到 0.95，但来源文档过期率也在上升，你会说系统变好了吗？这迫使我们承认：单指标不存在脱离任务风险的“越高越好”。

## 三、[肌] 四个反事实实验，比再加十个平均分更有用

所谓反事实实验，就是只替换链条中的一环，其余保持不变。这样你测到的不只是相关性，而更接近因果归因。

### 实验 1：Oracle context（把检索结果换成金标证据）

- 若答案大幅改善：瓶颈主要在检索或排序。
- 若仍然答错：问题更可能在生成、指令或证据利用。

### 实验 2：Oracle answer（固定金标答案，只评检索证据）

检查 top-k 中是否存在支持金标答案的证据，并看其排名。这里该用 evidence recall@k、MRR 或 nDCG，而不是让 LLM 看最终文风打分。

### 实验 3：Distractor injection（逐步加入高相似但无关的段落）

如果金标证据不变，只加几个“看起来很像”的干扰块，答案就翻转，问题不是召回不足，而是**噪声敏感性**。这直接检验 chunking、reranker 与生成器抗干扰能力的接口。

### 实验 4：Position sweep（把同一证据移到开头、中间、结尾）

*Lost in the Middle* 报告了一个关键现象：相关信息位于长上下文开头或结尾时，模型表现通常更好；放在中间时可能显著下降。

> “Performance can degrade significantly when changing the position of relevant information.”
>
> “只改变相关信息的位置，性能就可能显著下降。”

因此，普通 recall@k 只回答“证据进没进候选集”，却没有回答“证据是否以模型能稳定利用的形式送达”。可以把后者称为 **effective recall（有效召回）**：

```text
检索召回 = 证据在 top-k 里
有效召回 = 证据在 top-k 里，并且生成器在当前噪声、位置、格式下能用到
```

以上四个实验共同支持第一节的骨架论证：把管线拆开，并对每一环做可控替换，才能定位改动应落在哪里。

### 旁逸：这和软件测试是同一个形状

这里的论证结构，与软件工程里的单元测试 / 集成测试完全同构：

```text
只跑端到端测试       <=> 只看最终答案正确率
给 retriever 单测     <=> 检查证据覆盖与排序
给 generator 单测     <=> 喂金标上下文测忠实与正确
做集成测试            <=> 检查噪声、位置、格式的接口效应
```

很多 RAG 团队的问题不是“没有指标”，而是只有集成测试，没有单元测试。

## 四、[骨] 用条件链算一笔“可靠性账”

把一次成功回答拆成三个必要事件：

- R：检索到了充分证据；
- U：在 R 成立时，生成器正确利用了证据；
- A：在前两者成立时，最终答案满足任务要求。

那么端到端成功率应写成条件链：

```text
P(成功) = P(R) * P(U | R) * P(A | R, U)
```

注意，这不是假设三者独立；恰恰相反，条件符号保留了上游对下游的影响。

假设一套系统：

```text
P(R)        = 0.85
P(U | R)    = 0.80
P(A | R,U)  = 0.95
```

端到端成功率只有：

```text
0.85 * 0.80 * 0.95 = 0.646
```

单看每环都“不算差”，串起来却只有 64.6%。这和昨天 Agent 的 pass^k 可靠性账是同一个数学骨架：**链条会乘法收缩。**

现在比较两种优化：

- 把召回从 0.85 提到 0.90：成功率升到 68.4%；
- 把利用率从 0.80 提到 0.90：成功率升到约 72.7%。

这不是说生成永远更值得优化，而是说明：**优化优先级要看条件链中的真实瓶颈与可提升空间，不能凭团队归属决定。** 如果你只记录端到端分数，就根本算不出这笔账。

### 结构标注

这是统一数学框架段：把检索评测、生成评测和线上成功率接成一条可计算的偏差传导链。

### 最强反驳

“这些中间指标也是 LLM judge 打的，拆得再细不还是代理指标？”

这个反驳成立。拆解改善的是**可诊断性**，不自动保证测量有效。对策不是退回一个总分，而是给评委也做校准：

1. 抽取人工标注集，测 judge 与人的一致率；
2. 对答案顺序、长度和措辞做扰动，测翻转率；
3. 能用执行器验证的事实，优先用规则、数据库或代码验证；
4. 报告分项置信区间，不把 LLM judge 的小数点后三位当真值。

这正好接上 8 月 1 日的结论：指南针可以自动化，但指南针本身必须被评测。

## 五、[筋] 从离线 benchmark 过渡到线上报警

作者从“如何评价一个离线样本”过渡到工程问题：哪些信号应该持续监控。

建议保留一张最小故障看板，而不是只展示一个 RAG 总分：

| 层级 | 离线指标 | 线上可观测信号 | 主要责任环 |
|---|---|---|---|
| 检索覆盖 | evidence recall@k | 无证据回答率、查询零命中率 | 索引/embedding/reranker |
| 上下文聚焦 | context precision、噪声敏感性 | 被引用 chunk 排名、无关 token 比例 | chunking/reranker |
| 证据利用 | oracle-context 下正确率、位置敏感性 | 引用与答案主张的一致率 | prompt/generator |
| 生成忠实 | claim-level faithfulness | 无引用主张率、引用冲突率 | generator/guardrail |
| 最终任务 | correctness、task success | 用户纠错、升级人工、业务损失 | 全链路 |
| 评委质量 | 人机一致率、扰动翻转率 | judge 漂移、版本间偏差 | evaluation |

真正值得警惕的不是某个平均值下降，而是**哪一个条件概率先变了**。例如知识库更新后 P(R) 上升、P(U|R) 却下降，可能意味着“召回更多”只是塞进了更多噪声。

## 全文复盘

### 理解轨迹

```text
最终答错
  |
  +--> 从“换模型”退一步：先问故障在哪一环
  |
  +--> 从“有依据=正确”再拆一步：忠实 / 正确 / 相关
  |
  +--> 从“指标相关”推进到“替换一环”的反事实实验
  |
  +--> 用条件概率把局部指标重新接回端到端成功率
  |
  +--> 最后把评委也放进被评测对象，而不是当作真理源
```

### 终局问题

如果“检索到了”必须经过生成器才能被观测，而“生成器会不会用”又取决于检索结果的噪声和位置，那么 retriever 与 generator 真能被完全独立评测吗？我们需要的是模块分数，还是一组刻画接口效应的响应曲线？

### 术语表

| 英文 | 中文 | 本文含义 | 出现位置 |
|---|---|---|---|
| faithfulness | 忠实度 | 答案主张是否受给定上下文支持 | 第二节 |
| answer relevance | 答案相关性 | 是否正面回应问题 | 第一、二节 |
| context relevance | 上下文相关性 | 上下文是否聚焦而少噪声 | 第一节 |
| evidence recall@k | 证据召回率@k | 前 k 个结果是否覆盖必要证据 | 第三节 |
| oracle context | 金标上下文 | 用已知正确证据替换检索结果的干预 | 第三节 |
| effective recall | 有效召回 | 证据不只到场，而且能被模型稳定利用 | 第三节 |
| position sensitivity | 位置敏感性 | 答案质量随证据位置变化的程度 | 第三节 |
| conditional probability | 条件概率 | 保留上游状态后测下一环成功率 | 第四节 |
